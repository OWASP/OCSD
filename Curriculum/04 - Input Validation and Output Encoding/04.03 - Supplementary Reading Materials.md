# Supplementary reading – Input Validation and Output Encoding

This chapter explains how web application developers handle untrusted data safely, from the request that delivers it to the output that displays it.

## Untrusted data

A web application receives data from many sources it does not control:

- Form fields and uploaded files, including file names and file content
- URL paths and query parameters
- HTTP headers and cookies
- Request bodies, such as JSON and XML documents
- Responses from third-party APIs and services
- Messages from queues and webhooks
- Data read from databases and shared systems that other parties can write to

All data that crosses a trust boundary into the application is untrusted, no matter which field, header, or protocol carried it.
A request does not have to come from the application's own user interface.
Anyone can construct a request with any tool and send any value in any part of it.

Untrusted data can also arrive indirectly.
A display name saved during registration is still attacker-controlled when a later page reads it from the database and shows it to another user.
This is why stored attacks work: the malicious value entered the system long before the vulnerable output was rendered.

Most vulnerabilities in this module share one root cause.
An interpreter, such as a database engine, an operating system shell, an XML parser, or a browser, receives untrusted data mixed into its instructions and executes the data as if it were code.
This is called injection.

Three techniques limit what untrusted data can do, and each has a distinct job:

- Input validation rejects data the application does not expect, shrinking the attack surface at the boundary.
- Parameterized APIs keep data separate from code, so an interpreter can never mistake one for the other.
- Output encoding transforms data at the moment of output, so the destination interprets it as data.

Validation supports the other two but cannot replace them.
A name such as `O'Hara` is valid input and still breaks a concatenated SQL query, and a comment field that legitimately accepts punctuation can carry a script.
The primary defense against injection is the safe API or the encoding, applied where the data meets the interpreter.

## Four input-handling techniques

Developers use four related techniques, and choosing the wrong one is a common source of vulnerabilities:

- Validation checks whether input matches what the application expects and rejects it otherwise.
- Sanitization changes input by removing or neutralizing unwanted content, and is appropriate only when the application must accept content that mixes safe and unsafe parts, such as rich text.
- Normalization, or canonicalization, converts input to a single standard form before it is checked or compared.
- Encoding, or escaping, transforms data at output time so that a specific destination treats it as data.

Normalization must come before validation.
The same logical value often has several representations: percent-encoded characters in a URL, alternative Unicode forms of a letter, or a relative path that resolves inside or outside a directory.
A check applied to one representation can be bypassed with another if a later component decodes the data again.
The safe order is to decode and normalize once, validate the normalized value, and then process it.

After validation, convert input into typed values at the boundary.
A validated date string becomes a date object, a quantity becomes an integer, and a status becomes an enumerated value.
Code beyond the boundary then works with types the language guarantees, and no later component needs to re-parse a raw string.

## Server-side validation

Validation is a security control only where the caller cannot tamper with it.
Client-side validation, whether HTML form attributes or script, gives users fast feedback and reduces accidental errors.
It provides no protection, because a caller can disable it, modify the page, or skip the client entirely and send requests directly.
Every security-relevant rule must therefore be enforced again on the server, even when the client checks the same rule.

Effective validation is allowlist-based.
It defines what the application accepts, such as a type, a length range, a format, or a fixed set of values, and rejects everything else.
Blocklists that try to enumerate dangerous input fail repeatedly, because attackers find encodings and variations the list does not cover.

Validation operates at two levels:

- Syntactic rules check form: an integer, at most 200 characters, a date in a defined format, one of `pending`, `approved`, or `rejected`.
- Semantic rules check meaning against business logic: the delivery date is in the future, the quantity does not exceed available stock.

For structured input such as JSON or XML request bodies, schema validation applies the same idea to the whole document.
It enforces required fields, types, ranges, and the absence of unexpected fields before any business code runs.

Handle validation failures by rejecting the request.
Do not attempt to repair invalid input, because correction logic is easy to get wrong and hides attacks.
Return a generic error message, since detailed messages teach an attacker how to refine a payload.
Module 6 covers error handling and Module 7 covers logging these events safely.

Use the validation features of your framework or a maintained library rather than writing validation logic from scratch.
Take care with regular expressions: a poorly written pattern can be forced into catastrophic backtracking, letting a short crafted string consume the server's CPU.
This is known as a regular expression denial of service.
Prefer simple patterns, and test them against hostile input.

## Preventing injection

Parameterized APIs prevent injection by keeping the structure of a command fixed while data travels separately.
The interpreter receives the code and the data through different channels and can never confuse them.

A query built by concatenation lets input rewrite the query:

```text
query = "SELECT * FROM users WHERE name = '" + name + "'"
```

An input of `' OR '1'='1` changes what this query means.
A parameterized query keeps the meaning fixed for any input:

```text
statement = prepare("SELECT * FROM users WHERE name = ?")
statement.execute(name)
```

The same separation principle applies to each interpreter an application talks to:

- SQL: use parameterized queries or prepared statements for every statement that includes untrusted data.
- Object-relational mappers: safe by default, but their raw-query and native-fragment features reintroduce concatenation risks.
- NoSQL databases: validate the type and structure of input, because attacker-supplied objects can smuggle query operators into a filter.
- Operating system commands: avoid invoking a shell; call the program through an API that passes arguments as a separate list, and allowlist the permitted commands and arguments.
- LDAP: escape filter metacharacters or use an API that binds values safely.
- XML parsers: disable document type definitions and external entity resolution, which prevents XML external entity attacks that read files or reach internal systems.
- XPath: use an API that binds variables instead of concatenating expressions.
- Server-side templates: never place untrusted data into the template source itself; pass it to the template as data.
- HTTP headers: reject carriage return and line feed characters in values written to headers.

Escaping data for the target interpreter is a last resort for legacy interfaces without parameterized APIs, and it must use the interpreter's own escaping function rather than a homemade one.

Defense in depth still matters.
Run database access under a least-privilege account so that an exploited query cannot modify schema or reach other tables.
Validate input before it reaches the interpreter, so that obviously malformed data never gets that far.

## Encoding output for its context

Cross-site scripting occurs when untrusted data reaches a browser in a way that makes the browser execute it.
In reflected cross-site scripting the payload arrives in the request and returns in the immediate response.
In stored cross-site scripting the payload is saved and later shown to other users.
In DOM-based cross-site scripting client-side code itself inserts untrusted data into a dangerous location in the page.

The defense is to encode data at the point of output, using the encoding that matches the destination context:

| Output context | Required treatment |
| --- | --- |
| HTML body content | HTML entity encoding, such as `<` becoming `&lt;` |
| HTML attribute value | Attribute encoding, with the value in quotes |
| JavaScript data | Avoid direct placement; pass values via safely serialized data |
| URL parameter | Percent encoding of the value |
| CSS value | Avoid placing untrusted data in CSS where possible |

Encoding from one context does not protect another, which is why a single generic escaping function is not enough.
Encode exactly once, at output time, for the context in use.
Encoding on input corrupts stored data and still misses contexts the developer did not anticipate.

Modern templating engines encode HTML output automatically, and this default prevents most cross-site scripting.
The risk concentrates in the features that bypass it: raw-output flags in server templates, and client-side sinks that parse strings as HTML or code, such as writing to an element's raw HTML property.
Prefer APIs that treat data as text, and treat every use of a raw-output feature as a finding to justify.

When a feature requires users to submit rich content such as formatted comments, encoding is not an option, because it would display the markup instead of rendering it.
Use a maintained HTML sanitizer library that keeps an allowlist of safe elements and attributes and removes everything else.
Do not write a sanitizer or filter markup with regular expressions; browsers parse HTML in forgiving and surprising ways that such filters fail to anticipate.

For APIs, encode untrusted data correctly in JSON and serve responses with the correct content type, so browsers do not interpret a response as HTML.
Content Security Policy, the `HttpOnly` and `Secure` cookie attributes, and framework protections reduce the impact of a missed encoding.
They are defense in depth; output encoding remains the primary control.

## Testing input and output handling

Validation and encoding rules are testable requirements.

- Positive tests confirm that valid input, including edge cases such as names with apostrophes and accented characters, is accepted and preserved.
- Negative tests confirm that invalid input is rejected: wrong types, out-of-range values, oversized payloads, malformed structures, and unexpected fields.
- Boundary tests exercise minimum and maximum lengths and values.
- Attack-based tests send known injection and cross-site scripting payloads, including encoded and double-encoded variants, and verify they are stored inertly and rendered harmlessly.
- Output tests verify correct encoding in every context that displays untrusted data, including error pages and API responses.

Send test requests directly to endpoints rather than through the user interface, since attackers do the same and client-side validation must not be part of the result.
When a validation, injection, or encoding defect is fixed, add a regression test that reproduces the original payload.

Automated tools complement these tests.
Static analysis finds concatenated queries and raw-output template features; dynamic scanners and fuzzers generate hostile input at scale.
Tools do not replace tests derived from the application's own validation rules and output contexts.

## Applying validation and encoding to a review feature

Consider a feature that lets a signed-in customer post a review of a product.
A review has a product identifier, a star rating, and a comment, and the application shows recent reviews on each product page and returns them from a JSON API.

The inputs and their server-side validation rules:

- The product identifier must parse as the application's identifier type and refer to an existing product, and authorization for it follows Module 3.
- The rating must be an integer from 1 to 5.
- The comment must be text between 1 and 2,000 characters after Unicode normalization, with no rule forbidding punctuation, because `Great value, isn't it?` is a legitimate review.

The endpoint rejects any request that fails these rules with a generic error response.
Validated values are converted to typed objects: an identifier, an integer, and a string.

The insert uses a parameterized statement, so a comment containing `'); DROP TABLE reviews;--` is stored as those literal characters.
Validation did not need to forbid quotes; parameterization made them harmless.

On the product page, the template engine's automatic HTML encoding renders the comment, so a stored payload of `<script>...</script>` displays as text instead of executing.
The team decides reviews are plain text, so no sanitizer is needed and no raw-output feature is used.
The JSON API returns the comment through the framework's serializer with the JSON content type.

The rules produce traceable tests:

- A review with rating 5 and a comment containing an apostrophe is accepted and displayed exactly as written.
- A rating of 0, 6, or `"five"` is rejected.
- A 2,001-character comment is rejected, and a 2,000-character comment is accepted.
- A comment containing a script tag is stored inertly and rendered as visible text on the product page.
- A comment containing SQL metacharacters appears unmodified in the database and in the API response.
- Requests sent directly to the endpoint receive the same decisions as requests from the user interface.

Each test traces to a validation rule, a parameterized statement, or an output context, and the tests change when those rules change.
