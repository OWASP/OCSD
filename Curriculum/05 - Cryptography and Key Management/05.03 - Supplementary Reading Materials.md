# Supplementary reading – Cryptography and Key Management

Web applications use cryptography to keep data private, detect changes, and verify where data came from.

## Encryption, hashing, and encoding

Confidentiality protects data from unauthorized disclosure.
Integrity lets you detect unauthorized changes.
Authenticity lets you verify that data came from an expected source.

A cryptographic key is a value that controls an operation such as encryption or signing.
Encryption uses a key to turn unencrypted data, called plaintext, into ciphertext.
Decryption recovers the plaintext with the appropriate key.
An encrypted database backup can protect records if someone obtains a copy of the backup without access to its decryption key.
An application that can decrypt those records still needs authorization checks before it gives anyone access to them.

A cryptographic hash function calculates a fixed-length value called a digest.
The same input produces the same digest.
Secure hash functions make it hard to find an input for a given digest or to find two different inputs with the same digest.
When two inputs produce the same digest, the result is called a collision.
Use a current general-purpose hash such as SHA-256, part of the Secure Hash Algorithm 2 (SHA-2) family, when a cryptographic digest is needed.
Message Digest 5 (MD5) and Secure Hash Algorithm 1 (SHA-1) have known collision attacks and are unsuitable for new designs that rely on collision resistance.

A digest can help you check whether a downloaded file matches the publisher's release.
Compute the downloaded file's digest and compare it with the expected digest from a trusted source.
If an attacker can replace both the download and the published digest, they can make the values match.

Encoding changes how data is represented.
Base64, for example, represents bytes as text so they can travel through systems that expect text.
Anyone who knows the format can decode the text without a key.
A Base64-encoded key or token needs the same protection as its original bytes.

### Password hashing

An application that verifies user passwords needs a stored value it can check against a new login attempt.
An attacker who steals the stored password hashes can test guesses on their own computer without sending login requests, a process called offline guessing.
A password-hashing function such as Argon2id increases the computing work required for each guess.
The function uses a salt, a public random value that is unique to each stored password hash and can be kept with it.
Salts prevent attackers from applying one precomputed set of guesses to every stored hash, while the cost of the function slows guesses against each hash.
A fast digest such as SHA-256 leaves offline guesses cheap even when salted.
If passwords are stored with reversible encryption, anyone who obtains the decryption key and ciphertext can recover the passwords.
See [Module 2's password storage guidance](../02%20-%20Authentication%20and%20Credential%20Management/02.03%20-%20Supplementary%20Reading%20Material.md#password-storage) for work factors and migration of older hashes.

## Encryption and authenticated encryption

Symmetric encryption uses the same secret key to encrypt and decrypt data.
Public-key encryption uses a pair of related keys.
Anyone with the recipient's public key can encrypt data for that recipient, and the matching private key is needed to decrypt it.
Systems often combine public-key mechanisms for establishing or protecting a shared key with symmetric encryption for the data itself.
Obtain public keys from a trusted source so an attacker cannot substitute their own key.

Use authenticated encryption with associated data (AEAD) when an application needs to keep stored data private and detect tampering.
An AEAD operation produces ciphertext and an authentication tag, a short value computed with the secret key to help detect tampering.
The recipient checks the tag during decryption.
Associated data is optional metadata, such as a record identifier, that stays readable and is covered by the authentication check.
If the ciphertext, tag, or associated data fails verification, reject the result before any plaintext reaches application logic.

Advanced Encryption Standard in Galois/Counter Mode (AES-GCM) and ChaCha20-Poly1305 are widely used AEAD choices.
Use a maintained library or service whose authenticated encryption interface handles the encryption and authentication together.
A strong cipher can fail in an unsafe mode.
Electronic Codebook (ECB) mode, for example, exposes patterns because identical plaintext blocks encrypted under the same key produce identical ciphertext blocks.
An encryption mode without authentication can leave ciphertext open to tampering.

### Nonces and initialization vectors

An encryption operation may take an additional input called a nonce or an initialization vector (IV).
The algorithm and mode determine how that value must be generated.
For AES-GCM and ChaCha20-Poly1305, the nonce must be unique for each encryption with a given key, even when encrypting the same plaintext again.
Reusing a nonce with the same key can expose information about the plaintext and let an attacker create ciphertext that passes authentication.
These nonces can be stored or transmitted with the ciphertext.

Uniqueness and unpredictability are separate requirements.
For example, the older Cipher Block Chaining (CBC) mode requires an unpredictable IV, while a design using AES-GCM can ensure nonce uniqueness with a correctly managed counter.
Prefer a library or service that handles nonces for you.
If the caller supplies nonces, follow the library's guidance for generation and per-key usage limits, including across processes and after restarts.

## Message authentication and digital signatures

A message authentication code (MAC) is a tag computed from the message and a shared secret key.
A valid tag shows that someone with the shared key produced it for that message.
Every party that can verify a MAC with the shared key can also generate one.
A hash-based message authentication code (HMAC), such as HMAC-SHA-256, is a standard way to authenticate a message with a shared key.

A digital signature uses a private key to sign data and the corresponding public key to verify it.
A service that receives the public key can verify signatures without gaining the ability to sign.
A valid signature confirms that the signed content matches the signature and that the signing operation used the corresponding private key.
Trust in the signer depends on who controls that key and how the verifier obtained its public key.
In a document approval system, a signature can serve as evidence of approval if the process also establishes who used the signing key and what they approved.

For a software release, verify that the signing key is trusted to publish that package.
See [Module 10's artifact verification guidance](../10%20-%20Software%20Supply%20Chain%20Security/10.03%20-%20Supplementary%20Reading%20Material.md#hashes-signatures-and-provenance) for how that check fits into a release process.

Use the expected algorithm and key from trusted configuration, and verify the protected bytes before acting on their contents.
For example, when your application receives a webhook (an event notification sent over the web), verify it using the sender's documented procedure.
If that procedure has you compare MAC tags directly, use a library comparison designed to avoid revealing how many bytes matched through differences in processing time.
Even a valid tag leaves the receiver responsible for deciding whether the sender is authorized to request the action.

A valid message can be captured and sent again, a failure called replay.
For example, a genuine webhook may ask your application to process the same event twice.
Depending on the protocol, the receiver can check a signed or MAC-protected timestamp to limit how long a message stays valid and record authenticated event identifiers to detect repeated delivery.

A signed JSON Web Token (JWT) carries claims such as an account identity.
Its signature or MAC protects the claims against tampering.
The claims use a Base64 variant called `base64url`, which anyone can decode.
Use a maintained token library with an explicit list of allowed algorithms and a trusted source of keys for the expected issuer.
See [Module 2's token validation guidance](../02%20-%20Authentication%20and%20Credential%20Management/02.03%20-%20Supplementary%20Reading%20Material.md#json-web-tokens) for the checks needed before accepting claims.

## Secure randomness and resistance to guessing

A brute-force attack systematically tries possible values until it finds one that works.
Within the same symmetric encryption algorithm, a larger random key gives an attacker more possible values to search.
A key generated from a predictable input, such as a timestamp, can be easy to guess even if the key itself is long.

Secret tokens, such as password reset tokens, also need to be hard to guess.
Entropy is a measure of uncertainty in the source used to produce those values.
A cryptographically secure random number generator (CSPRNG) uses a source of entropy to produce values designed to be unpredictable.
Use the secure random interface documented by the operating system, language, or framework.
For keys that require a specific format, use the key generation function supplied by the cryptographic library or service.

Random functions designed for simulations, games, or sampling can produce output that looks random while remaining predictable.
The current time, process identifiers, and similar values are poor sources of entropy.
Let the platform manage its generator's internal state and supply it with entropy.

A password salt can be public, and generating it randomly helps keep it unique.
An encryption nonce can also be public in the schemes discussed above, and its generation must meet the requirements of the chosen scheme.

## Key agreement and public-key trust

Key agreement lets two parties derive a shared secret without sending that secret over the network.
Authentication establishes who the parties are sharing the secret with.
They can derive keys from the shared secret to protect the data they exchange during the session.

An X.509 certificate is a signed document that binds a public key to identity information such as a service's domain name.
A certificate authority (CA) signs the certificate to vouch for that binding.
A certificate chain links the certificate to an authority the verifier already trusts.

Ephemeral key agreement uses temporary key material for a connection.
Forward secrecy protects past sessions if a long-term private key is later stolen, provided the temporary secrets remain protected.

Transport Layer Security (TLS) combines these mechanisms.
In a typical certificate-based connection, the server presents a certificate and signs data from the handshake, the exchange that sets up the connection.
The parties derive session keys from a shared secret and use symmetric authenticated encryption to protect traffic.
See [Module 9's secure communications reading](../09%20-%20Secure%20Communications/09.03%20-%20Supplementary%20Reading%20Materials.md#tls-versions-and-downgrade-prevention) for protocol versions, cipher-suite selection, and certificate validation in deployed systems.

### Quantum computing and public-key cryptography

A sufficiently capable quantum computer could break widely used public-key schemes, including Rivest–Shamir–Adleman (RSA) and common elliptic-curve schemes for key agreement and signatures.
An attacker could record encrypted traffic today and try to decrypt it later if the key agreement scheme becomes vulnerable.
This matters for data that needs to stay confidential for years.
Post-quantum cryptography uses algorithms designed to resist attacks from both conventional and quantum computers.
Keeping track of the algorithms an application relies on helps developers plan replacements as guidance changes.

## Key management

### Generation, storage, and access

Generate keys through a maintained cryptographic library or key service and follow current guidance for the key's algorithm and purpose.
Use distinct keys for different purposes, such as signing and encryption, and for different environments, such as testing and production.
This limits what an exposed key can affect.
Transfer secret and private keys through approved, protected channels when they must leave their point of creation.

A key management service (KMS) can control access to keys and perform operations such as decryption on behalf of an application.
A hardware security module (HSM) is a hardware device designed to protect keys and perform cryptographic operations within a protected boundary.
Protected operating system keystores and managed secrets stores are other options, depending on how the application needs to access the material.

Keep secret and private keys out of source code, logs, and unprotected configuration and backups.
Store keys separately from the data they protect so that access to the data alone does not grant access to the keys.
Give each application identity permission to perform only the key operations it needs.
Record who owns each key, its purpose and version, and events such as changes in permissions, unexpected use, and retirement.
Keep key material out of those records.

### Rotation, compromise, and retirement

Rotation makes a new key or key version active for future encryption or signing.
Set the period for using a key based on its purpose, how much data it protects, applicable guidance, and the consequences if it is exposed.
Shorten that period if the algorithm's usage limits, changes in guidance, or system risk require it.

A key version identifier helps the application find the right key for existing data.
During routine rotation, a permitted older encryption key may remain available for decryption, and a trusted older public verification key may remain available to verify existing signatures.
Plan any data migration explicitly, including whether existing data needs to be re-encrypted and whether retained backups still depend on an earlier key.

Suspected compromise calls for a separate response.
Restrict use of the affected key, replace it, and revoke any associated credential or trust where appropriate.
Determine which data may have been disclosed and which messages can still be trusted.
Replacing a key protects future operations when the new key remains secure.
An attacker may still have copies of older data or validly formatted messages produced with the exposed key.

Keep older decryption keys under controlled access for as long as required to recover retained data.
Test restoration from backups and confirm that recovery still works with the relevant key versions.
Before destroying a key, check whether any retained data still relies on it and account for copies held in backups or replicas.
Data can become unrecoverable if its last usable decryption key is destroyed.

### Envelope encryption and key derivation

Envelope encryption separates the key that encrypts data from the key that protects that data key.
The application can store an encrypted copy of the data key with the ciphertext while access to the key that protects it stays under the key service's control.
Depending on the system and the reason for the change, it may be possible to protect the data key under a new key without re-encrypting the payload.
If the data key itself is compromised, protecting it with a different key leaves the compromised data key in use.

A key derivation function (KDF) produces one or more keys from input such as a shared secret or a password.
Systems use different functions for these inputs.
A protocol can derive distinct keys for different jobs from a shared secret, while a password-based function adds a deliberate cost to guessing the password.

## Protecting customer support exports

A support application keeps downloadable exports in object storage for 30 days.
The team wants a stolen copy of an export to remain private and the application to reject altered exports.
It chooses a maintained envelope encryption library that uses authenticated encryption and a key management service.
The library generates a new data key and manages the nonce for each export.
It authenticates the export identifier as associated data.
On download, the application supplies the expected identifier for the requested export so that substituting another export's ciphertext causes verification to fail.
The application still checks whether the requester may download that export.

After routine rotation, the key service uses the new key version to protect data keys for new exports.
The older version remains available to decrypt data keys for retained exports.
The team checks that exports created before and after rotation can be opened by authorized users, and that altered exports and mismatched identifiers are rejected.
It also tests that a failed key lookup returns no export and verifies that any older key version it plans to destroy is no longer needed by retained exports or backups.

## Additional learning resources

- [RFC 4648 – The Base16, Base32, and Base64 Data Encodings](https://www.rfc-editor.org/rfc/rfc4648.html) covers representations such as Base64 and `base64url`
- [National Institute of Standards and Technology (NIST) – Hash Functions](https://csrc.nist.gov/projects/hash-functions) summarizes the approved hash families and the transition away from SHA-1
- [NIST SP 800-38D – Recommendation for Block Cipher Modes of Operation: Galois/Counter Mode (GCM) and GMAC](https://csrc.nist.gov/pubs/sp/800/38/d/final) specifies GCM and its initialization vector requirements
- [RFC 8439 – ChaCha20 and Poly1305 for IETF Protocols](https://www.rfc-editor.org/rfc/rfc8439.html) specifies the AEAD construction and its nonce requirements
- [RFC 2104 – HMAC: Keyed-Hashing for Message Authentication](https://www.rfc-editor.org/rfc/rfc2104.html) defines HMAC
- [NIST FIPS 186-5 – Digital Signature Standard (DSS)](https://csrc.nist.gov/pubs/fips/186-5/final) specifies digital signature algorithms
- [RFC 5280 – Internet X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile](https://www.rfc-editor.org/rfc/rfc5280.html) describes certificates and chains of trust
- [RFC 9846 – The Transport Layer Security (TLS) Protocol Version 1.3](https://www.rfc-editor.org/rfc/rfc9846.html) describes how the handshake establishes shared keys and authenticates the server
- [NIST – What Is Post-Quantum Cryptography?](https://www.nist.gov/cybersecurity-and-privacy/what-post-quantum-cryptography) introduces the risks and explains why long-lived data can be affected
- [NIST SP 800-57 Part 1 Rev. 5 – Recommendation for Key Management: Part 1 – General](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) covers key lifetimes, recovery, and response to compromise
