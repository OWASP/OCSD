# Supplementary reading – Error Handling

This chapter covers handling errors so that failures do not disclose information or weaken security controls.

## Errors and their security impact

An error occurs when an operation cannot complete as intended.
Causes include invalid input, missing data, an unavailable database or service, an expired certificate, or exhausted memory or disk space.
Many programming languages report errors as exceptions, which interrupt normal execution until code handles them.

Errors are part of normal operation.
Users submit unexpected input, networks fail, and dependencies become slow or unavailable.
Attackers also cause errors deliberately to learn how an application behaves when something goes wrong.

Poor error handling can lead to:

- Information disclosure, when an error response reveals internal details
- Bypassed security checks, when a failed check results in access being granted
- Inconsistent state, when an operation stops halfway and leaves data or permissions partly changed
- Reduced availability, when errors consume resources or stop the application

Failure paths are often tested less than successful paths.
They need the same security review, because an attacker can usually choose which path the application takes.
The [OWASP Top 10:2025 A10 – Mishandling of Exceptional Conditions](https://owasp.org/Top10/2025/A10_2025-Mishandling_of_Exceptional_Conditions/) describes these risks.

## Information disclosure through errors

### Internal details in error responses

Framework and server defaults often show detailed error information to help developers.
In a deployed application, that information helps attackers.
Error responses can reveal:

- Stack traces, which list the code that was running, including class, function, and file names
- Source file paths and directory layout
- Framework, library, and server versions
- Database error messages, table names, and query fragments
- Internal hostnames, IP addresses, and service names
- Configuration values, including connection strings or secrets

Each detail narrows an attacker's search.
A version number can point to a known vulnerability.
A database error that includes part of the query can confirm an injection point and show how to adjust the attack.
[CWE-209: Generation of Error Message Containing Sensitive Information](https://cwe.mitre.org/data/definitions/209.html) describes this weakness.

### User-facing messages and diagnostic information

User-facing messages and internal diagnostic information serve different audiences.
The user needs to know what happened in general terms and what to do next.
Developers and support staff need the technical details, and those belong in internal records.

A safe response for an unexpected error contains a generic message and a reference identifier.
For example: "The request could not be completed. Reference: 7f3a9c."
Support staff can use the identifier to find the full details in the application's internal records.

Messages for input errors can be more specific when the detail concerns the user's own input.
"The date must be in the future" helps the user without revealing anything internal.
"Column 'expiry_date' violates constraint 'chk_future'" reveals the database schema.

### Observable differences between responses

An application can disclose information even when each message is generic.
Attackers compare responses for different inputs and look for differences in:

- Message text, such as "unknown user" versus "wrong password"
- HTTP status codes, such as 404 Not Found for missing records and 403 Forbidden for existing records the user cannot access
- Response times, such as a fast reply when an account does not exist and a slower reply when the application checks a password
- Redirects, headers, or response sizes

These differences let an attacker enumerate, or systematically discover, valid accounts, records, or resources.
A list of valid accounts makes password guessing and phishing more effective.

When the existence of an account or record must not be revealed, give every case the same response.
For example, a sign-in form returns "Invalid username or password" for both unknown users and wrong passwords.
A password reset form replies "If an account exists for this address, you will receive an email" in every case.
The application should also take similar time for each case, for example by performing a password hash comparison even when the account does not exist.
The [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages) gives further examples.

## Failing securely

### Fail-secure and fail-open behavior

A fail-secure (also called fail-closed) design denies access or stops the operation when an error prevents a security decision.
A fail-open design allows the operation to continue.
For security checks, the secure outcome is almost always to deny.

Consider an authorization check that calls a separate permissions service.
If the service times out, the application cannot know whether the user has permission.
A fail-open implementation treats the timeout as permission granted.
A fail-secure implementation denies the request and reports a temporary error.

The same applies to other security-relevant checks:

- If a session cannot be validated, treat the user as not signed in.
- If a certificate cannot be verified, do not connect.
- If an input validation routine fails, reject the input.
- If a fraud or rate-limiting check cannot be reached, decline or hold the transaction rather than processing it unchecked.

Some availability requirements tempt teams to fail open, for example to keep a shop running when a fraud check is down.
That is a business risk decision and should be made explicitly by the responsible owner, not introduced by a default in error handling code.
[CWE-636: Not Failing Securely ('Failing Open')](https://cwe.mitre.org/data/definitions/636.html) describes this weakness.

### Defaults and fallback logic

Code that sets a permissive value first and changes it later fails open if an error interrupts it.
For example, a variable `isAllowed` that starts as `true` and is set to `false` only after a successful check grants access when the check throws an exception.
Start from the restrictive value and grant access only after a check succeeds.

Fallback logic deserves the same review.
Retrying with weaker settings, skipping a check, or using cached permissions after an error can turn a temporary fault into a security bypass.

### Consistent state and resources

An operation that stops partway can leave data inconsistent.
For example, a transfer that debits one account and then fails before crediting the other has lost money.
A role change that removes old permissions but fails before recording the change can leave an account with unexpected access.

Use transactions so that related changes are applied together or not at all.
When a transaction is not possible, for example across separate services, define compensating steps that undo completed work.

Release locks, database connections, file handles, and temporary files on every path, including failure paths.
Most languages provide constructs for this, such as `finally` blocks or automatic resource management.
Leaked resources can exhaust connection pools or disk space, and an attacker who can trigger the error repeatedly can make the application unavailable.

## Exception handling practices

### Handling errors at the right layer

Catch specific exception types that the code knows how to handle.
A handler that catches every possible error also catches errors the developer did not anticipate and may handle them incorrectly.

Handle an error where there is enough context to choose a safe response.
A low-level database function often cannot decide what the user should see.
It can add context and pass the error on.
A higher layer, such as the request handler, can then decide on the response.

### Swallowed exceptions

An exception handler that ignores the error, or only records it and then continues, is said to swallow the exception.
The application continues as if the operation succeeded.
If the operation was a security check, an audit record, or a data update, the failure goes unnoticed and the application may continue in an unsafe state.
[CWE-390: Detection of Error Condition Without Action](https://cwe.mitre.org/data/definitions/390.html) describes this weakness.

Every handler should do at least one of the following: recover correctly, record the error and stop the operation, or pass the error to a layer that can handle it.

### Unhandled exceptions

An exception that no code handles reaches the framework or runtime.
Depending on configuration, the framework may display a detailed error page, return an empty response, or stop the process.
Know the framework's default behavior and configure a safe handler for errors that reach it.

### Wrapping and translating errors

Wrapping an exception means creating a new exception that adds context and keeps the original as its cause.
This preserves the technical details for internal diagnosis.

At a trust boundary, translate internal errors into responses suitable for the recipient.
An application returns a generic message to its clients.
A service called by other services returns a defined error code rather than its internal stack trace.
The original details stay in the internal records of the system where the error occurred.

## Centralized error handling and error responses

### Global handlers

Most web frameworks support a global exception handler or error-handling middleware.
It receives errors that request handlers did not handle and produces the response.
A central handler ensures that every unhandled error produces the same safe response, records the details, and returns a reference identifier.
It also avoids repeating error handling code in every request handler, where one omission can expose details.

Errors can occur before application code runs, for example in the web server, a reverse proxy, or request parsing.
They can also occur in background jobs and asynchronous tasks that have no user-facing response.
Configure custom error pages in each component that can produce one, and handle errors in background work so they are recorded rather than lost.

### Error pages and API error formats

Replace default framework and server error pages with custom pages that contain no internal details.
Check every status code users can encounter, including 400, 401, 403, 404, 405, 500, and 503.

APIs benefit from a consistent error format that clients can process reliably.
[RFC 9457: Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457) defines a standard format with fields such as `type`, `title`, `status`, and `detail`.
The `detail` field should describe the problem for the client, not expose internal information.

### Status codes

HTTP status codes tell clients the category of an error.
Codes in the 400 range indicate a problem with the request, such as invalid input, a missing or invalid authentication (401 Unauthorized), or a lack of permission (403 Forbidden).
Codes in the 500 range indicate a problem on the server.
Use the code that matches the category, and keep internal details out of the response body.
When the existence of a resource must not be revealed, return the same code for missing resources and resources the user may not access, as described in [observable differences between responses](#observable-differences-between-responses).

## Error modes and configuration

Frameworks often provide a development mode that shows detailed error pages, stack traces, and interactive debugging tools.
These features help during development and are dangerous in production.
Some debugging tools allow code execution from the browser, which gives an attacker control of the server.

Production configuration should:

- Disable detailed error pages and stack traces in responses
- Disable or remove debugging tools and diagnostic endpoints
- Return generic error responses and record details internally

Secure defaults reduce the chance of mistakes.
Detailed error output should be disabled unless the configuration explicitly enables it for a development environment.
A missing or misspelled setting should then result in the safe production behavior.

Environment-based configuration selects the right settings for each environment.
Deployment checks can confirm that production does not run in a debug mode, for example by requesting a missing page and checking the response for framework details.
The [OWASP Top 10:2025 A02 – Security Misconfiguration](https://owasp.org/Top10/2025/A02_2025-Security_Misconfiguration/) covers related configuration risks, and Module 14 covers secure configuration for deployment.

## Error diagnosis and testing

### Recording errors for diagnosis

Internal error records let developers diagnose problems that users cannot describe.
Useful details include:

- The time of the error
- A request or correlation identifier that links related records, including the reference shown to the user
- The error type and message
- The operation being performed
- Relevant context, such as the user identifier and the resource involved

The stack trace belongs in these internal records, not in the response.

Error records can capture sensitive data by accident, for example when an exception message includes a request body or a connection string.
Exclude passwords, tokens, session identifiers, keys, and sensitive personal data from recorded error details.
Module 7 covers secure logging, including protection and retention of log data.

### Testing error handling

Test failure paths as deliberately as successful ones.
Useful test cases include:

- Trigger errors with invalid input, missing parameters, unexpected types, and oversized requests, and check that responses contain no internal details
- Simulate unavailable dependencies, such as the database or an authorization service, and check that access is denied and state remains consistent
- Compare responses for existing and non-existing accounts or records, including status codes and timing, where these must not be distinguishable
- Request missing pages and unsupported methods in a production-like environment, and check that custom error pages are returned
- Check that recorded errors contain the expected diagnostic details and no secrets

The [OWASP Web Security Testing Guide: Testing for Error Handling](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/08-Testing_for_Error_Handling/README) describes how testers look for error handling weaknesses.

## Reviewing an invoice download endpoint

Consider a fictional billing application in which customers download their invoices.
The endpoint receives an invoice number, asks a separate permissions service whether the customer may view it, and returns the file.

During a review, the team finds three problems.

First, the permission check is wrapped in a handler that catches every exception and continues.
When the permissions service times out, the handler records nothing and the download proceeds.
This is a fail-open design and a swallowed exception.
The team changes the code to deny the request when the check fails, return a temporary error, and record the failure with a request identifier.
A new test simulates a timeout and checks that no invoice is returned.

Second, requesting an invoice number that contains letters causes a database error.
The response shows the framework's default error page with the SQL query and the server's file paths.
The query fragment shows that the invoice number is inserted directly into the SQL text, which suggests an injection vulnerability.
The team changes the lookup to a parameterized query, as described in Module 4, and adds input validation for the invoice number.
Hiding the error alone would not have fixed the injection.
They also configure the global exception handler to return a generic message with a reference identifier, and confirm that the production configuration disables the framework's debug mode.

Third, the endpoint returns 404 Not Found for invoice numbers that do not exist and 403 Forbidden for invoices that belong to other customers.
An attacker can use this difference to discover valid invoice numbers.
Existing invoices also respond more slowly, because only they trigger the call to the permissions service.
The team changes the endpoint to look up invoices only among those belonging to the signed-in customer.
Missing invoices and other customers' invoices now follow the same path and return the same 404 Not Found response.
The permission check still runs for invoices the customer owns, so a permissions service outage no longer reveals whether another customer's invoice exists.
A test compares the status code, body, and response time for both cases.

After the changes, the team checks that the internal error records contain the request identifier, error type, and invoice number, but no session tokens or file contents.
