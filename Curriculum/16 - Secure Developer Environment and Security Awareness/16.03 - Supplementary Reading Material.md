# Supplementary reading – Secure Developer Environment and Security Awareness

This chapter covers protecting the workstations, tools, and services developers use, and recognizing attacks aimed at developers.

## Threats to development environments

A developer workstation often has more access than a typical office computer.
It may hold source code, signing keys, cloud and cluster configuration, and sessions for code hosting, package registries, and internal systems.
Developers also install tools, run code from many sources, and change system settings more often than other users.

An attacker who controls a developer workstation can act with that developer's access.
They may read or change source code, steal credentials, reach internal systems, or change what goes into a release.
A single compromised workstation can therefore affect the organization's software and its users.

Assets to protect in a development environment include:

- Source code and internal repositories
- Passwords, API keys, access tokens, SSH keys, and signing keys
- Cloud profiles, cluster configuration files, and other stored credentials
- Build and deployment settings
- Test data, database exports, logs, and debugging output
- Browser sessions for code hosting, cloud consoles, and single sign-on

Common entry points include malicious packages and extensions, untrusted repositories, phishing, secrets left in files, sensitive data pasted into online tools, and lost or stolen devices.

## Workstation protection

### Least privilege and separation

Least privilege means using only the access a task requires.
Routine development should use a standard account rather than an administrator or root account.
From an administrator account, a program or malicious script is often one confirmation prompt or `sudo` command away from full privileges.
Developers who approve such requests out of habit give that access away.
Request elevated rights only for the task that needs them.

Keep development, test, and production access separate.
Use separate profiles or accounts for each environment so that a development command cannot change production by mistake.
Keep work and personal activity apart, for example by not using a work device for personal browsing or personal projects.

### Layered device controls

Defense in depth means relying on several controls so that the failure of one does not expose everything.
On a workstation, these controls commonly include:

- Full-disk encryption, which protects stored data if the device is lost or stolen
- Automatic screen locking and a strong sign-in method, which protect an unattended device
- Endpoint protection, which detects and blocks known malicious software and suspicious behavior
- A host firewall, which limits incoming network connections
- Timely updates for the operating system, browsers, development tools, and runtimes

Remove software, accounts, and services that are no longer needed.
Each one adds code that can contain vulnerabilities.

### Physical security

Lock the screen when leaving a device, even briefly.
Do not leave devices or hardware security keys unattended in public places.
Before sharing a screen, close windows and terminals that show secrets, customer data, or internal details.
Do not let family members or visitors use a work device.

## Policies and responsibilities

Organizational security policies record decisions about acceptable risk.
Policies that commonly affect developers cover:

- Acceptable use of company devices and networks
- Installation of software, including development tools and extensions
- Approved tools, online services, and code assistants
- Data classification and handling, including which data may appear in test environments and logs
- Production access
- Remote work

Production access should be limited to the people and time a task requires, and it should be logged.
Standing administrator access to production increases the impact of a stolen credential.

Workstation security is a shared responsibility.
Developers protect their credentials and follow policy.
Managers give teams time for updates and training and avoid pressure to bypass controls.
Security teams provide practical guidance and respond to incidents.
IT teams provision, update, and manage devices.

Report promptly when:

- A device, hardware security key, or storage device is lost or stolen
- A secret may have been committed, logged, shared, or otherwise exposed
- Suspicious software, an extension, or a package was installed
- Endpoint protection raises an alert
- Unexpected sign-in attempts, MFA prompts, or account activity appear
- Sensitive data was sent to an unapproved service

Early reports give security teams time to revoke credentials, end sessions, and isolate devices before more damage occurs.
If a control prevents legitimate work, raise the problem through the proper channel rather than working around it.

## Local development tools

### What local tools can access

IDEs, editors, extensions, language servers, and command-line tools run with the developer's permissions.
They can usually read workspace files, start processes, use the terminal, read environment variables, and connect to the network.
A malicious or compromised extension can therefore copy source code and credentials or change files before they are committed.

Before installing an extension or tool, check:

- Whether the publisher is the expected one
- Which permissions or capabilities it requests and whether they fit its purpose
- Whether it is maintained and receives security fixes
- Whether the organization provides an approved list or alternative

Remove extensions and globally installed tools that are no longer used.

### Code that runs when a project opens

Opening, building, or testing a repository can run code without an explicit command.
Examples include:

- Editor task definitions and workspace settings that start tools automatically
- Build scripts and test configuration
- Package installation scripts that run during dependency installation
- Git hooks installed by a package or build script, which then run during operations such as commits and checkouts

Git does not copy hooks when a repository is cloned.
A repository's hooks run only after something installs or enables them, such as a hook manager started by a package installation script.

Many editors offer a workspace trust or restricted mode.
In this mode, the editor disables features that could run code from an unfamiliar folder until the user trusts it.
Open unfamiliar repositories in restricted mode, and review their configuration before trusting them.
[Visual Studio Code Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust) is an example of such a feature.

Installation guides sometimes suggest downloading a script and piping it straight into a shell.
This runs content that has not been reviewed and that can change between downloads.
Download the script, review it, confirm its source, and run it with the least privilege it needs.
Apply the same care to commands copied from documentation, forums, or chat.

Review your own changes before committing them.
Checking the diff catches secrets, debugging changes, and unexpected modifications, including changes made by a compromised tool.

[Module 10](../10%20-%20Software%20Supply%20Chain%20Security/) covers the review of packages and dependency updates.
On a workstation, remember that installation scripts and build plugins run with the developer's local access, including stored credentials.

## Online services and code assistants

### Data submitted to online services

Developers use online services to format data, decode tokens, test regular expressions, convert code, and analyze errors.
These services may store, log, or reuse what is submitted.
Paste sites and public snippets can be indexed by search engines and collected by automated tools.
A free service may be funded by collecting or analyzing user input.

Do not submit the following to an unapproved service:

- Passwords, API keys, tokens, private keys, and session cookies
- Proprietary source code
- Personal data, customer records, or production data
- Logs or configuration that reveal internal systems
- Security findings or incident details

Before using a service with work data, check whether the organization approves it for that type of data.
Data handling terms describe retention, use, and sharing of submitted data.
Prefer local tools, approved services, or sanitized inputs.
For example, decode a token with a local tool, or replace real values with placeholders before asking for help.

### Code assistants

Code assistants send prompts and surrounding code to a model for processing.
Depending on the service and configuration, that content may be retained or used outside the organization.
Use only assistants and settings the organization has approved for the code and data involved.

Generated code, commands, and dependency suggestions can be insecure or incorrect.
A suggested package may not exist, or its name may already be registered by an attacker.
Review generated output in the same way as other untrusted code before running or committing it.
The developer remains responsible for code, commands, and dependencies, regardless of how they were produced.

## Secrets and sensitive data

### Keeping secrets out of code

A secret is a value that grants access, such as a password, API key, access token, private key, or session cookie.
Secrets do not belong in source code, configuration templates, documentation, comments, or container images.
Anyone with access to the repository or image can read them, and copies can persist long after a change.

Applications should obtain secrets at runtime from an approved secret store or the deployment environment.
Local environment files can hold development values when policy allows it.
Exclude them from version control, and commit only an example file containing placeholder values.
Do not keep production secrets in local files.

Prefer credentials that are limited in scope and expire quickly.
A token that can read one repository for one day causes less harm when exposed than a token with broad access that never expires.

### Responding to an exposed secret

Version control keeps the history of every commit.
Deleting a secret in a later commit does not remove it from history, forks, or clones.
Treat a committed secret as exposed.

When a secret is exposed:

1. Revoke or rotate it so the exposed value no longer works.
2. Remove it from the current code and configuration.
3. Report the exposure according to the organization's process.
4. Check logs for use of the exposed value.
5. Follow the organization's process if history must be rewritten.

Revocation comes first because rewriting history does not invalidate copies that others may already have.
[GitHub: Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) explains why history cleanup alone is not enough.

### Secret detection

Secret detection tools search for values that look like secrets.
Running them before each commit catches mistakes before the secret leaves the workstation.
Running them in shared repositories catches secrets that local checks missed.
Pattern-based detection can miss secrets with unusual formats and can report values that are not secrets, so it supplements careful review.
The [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html#8-detection) describes detection approaches.

### Test data and diagnostic information

Use synthetic or anonymized data for development and testing.
Copy production data to a workstation only with approval and the protection its classification requires.

Logs, stack traces, screenshots, and crash reports can contain tokens, cookies, authorization headers, and personal data.
Remove or replace these values before sharing diagnostic information in tickets, chat, or external services.

## Networks, remote access, and local services

### Networks and remote access

Developers work from offices, homes, and public places.
Home and public networks are outside the organization's control.
Other devices on the same network may be compromised, and public networks may be operated by an attacker.

Basic home network protections include changing default router passwords, keeping router firmware updated, using current Wi-Fi encryption, and placing visitors and smart devices on a separate network.
On public networks, use the organization's approved remote access method and do not ignore certificate warnings.

Use the remote access mechanisms the organization provides.
Unofficial tunnels, personal remote access tools, and shared access credentials bypass the organization's authentication, monitoring, and access controls.

### SSH keys

SSH private keys grant access to servers and code hosting.
Protect them with a passphrase, store them only on devices you control, and never share or commit them.
Remove keys that are no longer needed from the systems that accept them.

A host key warning means the server's identity differs from the one previously recorded.
Treat it as a possible interception until the change is confirmed through another channel.
Agent forwarding lets a remote server use the developer's loaded keys while connected.
An administrator or attacker on that server can then use those keys, so enable forwarding only when required and only for trusted hosts.

### Local development services

Development servers, databases, dashboards, and debuggers often run without authentication or with default credentials.
Bind them to the local machine rather than to all network interfaces unless other access is required.
A service bound to all interfaces may be reachable by other devices on a home or public network.

Do not use production credentials in local services.
Run them without administrator privileges, so that a compromised service cannot take over the workstation.
Stop services when they are no longer needed.
Publishing a local service through a public tunnel or port forwarding exposes it to the internet and requires approval and authentication.

## Containers, virtual machines, and managed workspaces

### Isolation and its limits

Containers, virtual machines, development containers, and cloud workspaces separate project tools and dependencies from the host.
They can limit the impact of untrusted code and make environments easier to reproduce and replace.

A container shares the operating system kernel of the machine that runs it.
On Linux, that is the host's kernel.
Desktop container tools on macOS and Windows usually run containers inside a lightweight Linux virtual machine, but host folders and the container runtime socket can still be shared into it.
A virtual machine runs its own operating system and usually provides stronger isolation.
Both depend on configuration, and neither makes untrusted code safe on its own.

### Configurations that weaken isolation

These container settings reduce or remove isolation:

- Privileged mode gives the container broad access to host devices and kernel features.
- Mounting the container runtime socket, such as the Docker socket, lets the container control the runtime and start new containers with host access.
- Mounting a home directory or other broad host paths exposes SSH keys, cloud credentials, and other files.
- Running as root inside the container increases the impact of an escape or a misconfiguration.

Mount only the directories a task needs, and use read-only mounts where possible.
The [OWASP Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) describes these risks.

Use images from trusted sources and keep them updated.
Do not place secrets in images or image build files, because anyone who can obtain the image can extract them.

### Shared data and leftover environments

Shared folders, a shared clipboard, and forwarded credentials connect a virtual machine or workspace back to the host.
Limit them when working with untrusted code.

Snapshots, workspace logs, and stopped environments can retain secrets and data.
Delete environments and snapshots that are no longer needed.

## Social engineering, compromise, and security awareness

### Social engineering aimed at developers

Social engineering manipulates people into revealing information or performing actions.
Attacks aimed at developers include:

- Phishing messages that imitate code hosting, cloud, or package registry notifications
- Messages that impersonate a colleague, manager, or IT support and ask for credentials or urgent changes
- Repositories, coding tests, or sample projects that run malicious code when opened or built
- Pull requests that hide harmful changes among legitimate ones

Verify unexpected requests for credentials, access, or code execution through a separate, trusted channel.
For example, contact a colleague through the company directory rather than replying to the message.
Support teams and legitimate messages do not ask you to send or read out passwords or MFA codes.
Enter them only on the genuine sign-in page, reached by navigating there yourself rather than through a link in the message.

### Indicators of compromise

Possible signs of a compromised workstation or account include:

- Sign-in alerts or MFA prompts the developer did not trigger
- Commits, branches, tokens, or access keys the developer did not create
- New or changed extensions, startup items, or shell configuration
- Unexpected processes, network connections, or endpoint protection alerts
- Password reset messages or changed account settings

### First responses

When compromise is suspected:

1. Stop the suspicious activity, such as a running script or an open session.
2. Preserve information about what happened, and avoid deleting files or wiping the device unless instructed.
3. Revoke or rotate exposed credentials and end active sessions where the developer can do so.
4. Report through the organization's incident process.

The incident team decides how to investigate and recover.
Wiping a device before reporting can destroy the information they need.

### Staying informed

Vulnerabilities in languages, frameworks, dependencies, and tools are published continuously.
Useful sources include security advisories from package ecosystems and code hosting platforms, vendor bulletins, organizational guidance, and OWASP resources.
The [CISA Known Exploited Vulnerabilities Catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) lists vulnerabilities with evidence of active exploitation, which helps prioritize updates.

## Responding to a suspicious sample project

Consider a developer who maintains a library that the company provides to customers.
The developer receives a message from someone claiming to be an engineer at a customer.
The sender asks the developer to clone a sample project that reproduces a bug and to run it before a call later that day.

The urgency and the request to run unfamiliar code are both warning signs.
The developer checks with the customer's account manager, who has no record of the sender.
The developer opens the repository in the editor's restricted mode instead of trusting it.
The project's configuration includes a task that runs automatically when the folder is trusted.
The package manifest also has an installation script that downloads and runs a remote file.

The developer does not trust the folder or install dependencies on the workstation.
A disposable virtual machine without shared folders or work credentials could limit the impact of running the project.
Because the installation script is clearly suspicious, the developer stops instead.

The developer reports the message and the repository through the organization's process.
They also mention that they cloned the repository on their work device.
The security team checks the device and confirms that none of the repository's code ran.

If the task had already run, the developer would stop it, rotate the credentials available on the device, end active sessions, and leave the device for the security team to examine.
Verifying the sender, reviewing before trusting, and reporting early kept the developer's access out of the attacker's reach.
