# Module 14 – Secure Configuration and Deployment

This outline defines the secure configuration and deployment knowledge assessed in Module 14.

## 14.1 Secure configuration principles

- Security misconfiguration as a cause of vulnerabilities in otherwise secure code
- Secure defaults, and the risks of default credentials, sample applications, and features enabled by default
- Hardening by disabling or removing unneeded features, services, accounts, and HTTP methods
- Attack surface reduction across the application, its servers, and its hosting platform
- Consistent configuration across environments, defined and reviewed as code where possible
- Configuration drift and undocumented manual changes in production

## 14.2 Web and application server configuration

- Serving only the intended public directory and file types
- Preventing access to source control metadata, environment files, backups, and other files not meant for clients
- Disabling directory listings unless explicitly intended
- Preventing execution of files in directories that store uploaded or generated content
- Restricting administrative interfaces, monitoring endpoints, and internal API documentation to authorized users and networks
- Limiting version and technology information in responses and default pages
- File and directory permissions that separate read-only application code from writable runtime data

## 14.3 Preparing a release for production

- Disabling debug modes, development tools, and diagnostic endpoints in production
- Excluding test code, test accounts, sample data, and test-only routes from production builds
- Excluding development dependencies and build tools from the deployed artifact
- Removing unused features, components, files, and documentation from the deployed application
- Risks of source maps, backup files, and leftover files in deployed web content
- Separate build and runtime stages that limit what reaches production

## 14.4 Configuration and secrets in deployment

- Separation of configuration from code so that one build can be deployed to different environments
- Separate credentials and configuration for development, test, and production environments
- Providing secrets to applications at runtime from a secret store or the deployment platform
- Platform-managed identities and short-lived credentials in place of stored credentials
- Exposure of secrets through images, deployment files, environment variable dumps, logs, and error output
- Least-privilege access to secrets, and rotation or revocation after exposure or on a schedule

## 14.5 Runtime identities and environment hardening

- Running applications and services under dedicated, non-administrative identities
- Separate identities for separate components, and the risk of sharing one identity across services
- Least-privilege permissions for runtime identities to files, databases, networks, and cloud resources
- Container hardening: non-root users, minimal base images, read-only file systems, limited capabilities, and resource limits
- Sandboxing and resource limits offered by the operating system's service manager
- Restricting outbound network access and inbound exposure of internal services

## 14.6 Security headers and browser policies

- Setting security headers consistently for all responses, including error responses and static content
- The purpose of `X-Content-Type-Options: nosniff`, `Referrer-Policy`, and `Cache-Control` for sensitive responses
- Content Security Policy (CSP) as a deployed policy, including report-only rollout and violation reporting
- The CSP `frame-ancestors` directive for preventing unwanted framing (clickjacking)
- Cross-Origin Resource Sharing (CORS) as a controlled relaxation of the same-origin policy
- Unsafe CORS configurations: reflecting the request's origin without validation, trusting the `null` origin, and loose origin matching, especially when credentials are allowed
- Why CORS does not replace authentication, authorization, or protection against cross-site request forgery
- The relationship to HTTP Strict Transport Security (HSTS) in Module 9 and to CSP as an XSS defense in Module 4

## 14.7 Managed platforms and cloud services

- The shared responsibility model for platform-as-a-service, container, and serverless hosting
- Platform settings that application teams control: HTTPS enforcement, minimum TLS version, network access restrictions, and authentication options
- Disabling unused remote access, remote debugging, and deployment endpoints on managed platforms
- Access controls on storage, databases, and other cloud resources used by the application
- Separation of production and non-production environments, including staging slots and preview deployments

## 14.8 Deployment pipelines and releases

- Least-privilege permissions for pipeline and deployment identities
- Short-lived, federated credentials for deployments in place of stored long-lived credentials
- Protection of pipeline secrets from untrusted code, pull requests, and logs
- Protected branches, required reviews, and approvals for production deployments
- Commit signing and its limits as evidence of who made a change
- Pinning third-party pipeline components to verified versions
- Deploying only artifacts that passed verification, as described in Module 10
- Rollback to a known good release after a failed or harmful deployment

## 14.9 Verifying configuration

- Automated checks of configuration files, infrastructure as code, and container images before deployment
- Tests that check deployed applications for debug features, exposed files, directory listings, and missing security headers
- Detection of configuration drift and unexpected changes in production
- Review of configuration changes alongside code changes
