# Module 15 – Security of and for AI

This outline defines the knowledge assessed in Module 15 for applications that use large language models.

## 15.1 Model-backed features in an application

- Parts of a model-backed feature: the model, the system prompt, user input, retrieved content, tools, and the destination of the output
- Which of those parts the application controls and which it obtains from a provider or a third party
- The context window as the limit of what a model can take into account
- Trust boundaries between user input, retrieved content, tool results, and model output
- Non-deterministic output and its consequences for testing and for controls that depend on an exact response
- The difference between securing a model and securing an application that consumes one
- The relationship between a model-backed feature and the application's existing authentication, authorization, and logging

## 15.2 Prompt injection

- Why a model cannot reliably separate instructions from data within its context
- Direct prompt injection through user input
- Indirect prompt injection through retrieved documents, fetched web content, and tool results
- Cross-modal prompt injection through images, audio, and other non-text input
- Sources of untrusted content that reach a prompt, including other systems' output and previous conversation turns
- What system prompt wording, delimiters, input filtering, and classification achieve, and why none of them creates a trust boundary
- Limits on what the model can reach and do, which hold once a prompt has been subverted
- Human confirmation before consequential or irreversible actions

## 15.3 Context, disclosure, and hidden instructions

- Content that reaches the model: prompts, system instructions, retrieved documents, tool schemas, and conversation history
- How a system prompt or tool schema can be extracted, and why no control may depend on keeping one secret
- Credentials, connection details, and access rules that must not be placed in a system prompt or tool schema
- Disclosure of personal or confidential information through model output, logs, traces, and error messages
- Retention of prompts and outputs by a model provider, and their use for training
- Limiting what is sent to a model and what is returned to the caller
- Privacy obligations that apply to data processed by a model, including deletion requests

## 15.4 Model access to data, tools, and actions

- The permissions held by a model-backed feature and the identity under which it acts
- The distinction between read access, write access, and the ability to trigger effects in other systems
- Tool access scoped to the operation at hand, and the risk of granting the application's full privileges
- Approval steps for actions with financial, destructive, or irreversible consequences
- Checking the requesting user's rights for each action, and why the feature's own permissions are not enough
- Logging of model-initiated actions in enough detail to reconstruct what was done and on whose behalf
- Excessive agency through excessive functionality, excessive permissions, or excessive autonomy

## 15.5 Retrieval, embeddings, and vector stores

- The role of embeddings and a vector store in retrieval-augmented generation
- Retrieved content as untrusted input to the prompt
- Access control and tenant isolation for a vector store, and leakage of one tenant's content to another
- Authorization enforced inside the index query, since filtering results afterward still leaks through result counts, scores, and timing
- Poisoning of an index through the documents and sources it ingests
- What an embedding can reveal about the text it was derived from
- Retention and deletion of indexed content alongside its source records

## 15.6 Model and data supply chain

- Model weights, adapters, fine-tuning data, and datasets as supply chain components
- Provenance, integrity verification, and trusted sources for model artifacts
- Poisoning introduced during pre-training, fine-tuning, adapter creation, embedding generation, or retrieval ingestion
- Misrepresentation of a model artifact's origin, contents, or licensing
- Libraries, runtimes, and serialization formats used to distribute and load model artifacts
- Why evaluation results do not rule out behavior planted in a model
- The relationship to the general component practices covered in Module 10

## 15.7 Consumption, cost, and extraction

- Cost and availability exposure from uncontrolled inference, including denial of wallet
- Limits on requests, tokens, and cost per user, per session, and per tenant
- Constraints on input size, output length, and processing time
- Model extraction and distillation through repeated querying of an exposed model
- Information that accelerates extraction, such as returned probabilities or verbose diagnostics
- Monitoring for usage patterns that indicate abuse or extraction

## 15.8 Handling model output

- Model output as untrusted input to whatever consumes it
- Handling required by each destination, including HTML, Markdown, shell commands, database queries, file paths, and onward API calls
- Rendering risks in chat interfaces, including links, images, and embedded markup
- Control characters in model output written to terminals, log files, and IDE panes
- Schema validation of structured output, which catches malformed responses but not a malicious value in a well-formed one
- Code produced by a coding assistant, including insecure patterns and references to packages that do not exist
- Content filtering and safety guardrails as defense in depth, and why filtering cannot make an unsafe destination safe

## 15.9 Reliability of model output

- Why fluent, confident output says nothing about whether it is correct
- Responses grounded in verified sources, with those sources shown to the user
- Confirmation of model output before it is relied on in consequential workflows
- Overreliance by developers reviewing generated code and by users reading generated content
- Evaluation and regression testing of a model-backed feature as its prompts, models, and sources change
