# Supplementary reading – Business Logic Security

This chapter covers flaws in business rules and workflows, and the controls that keep an application's features from being used in ways the business did not intend.

## Business logic flaws

### What business logic is

Business logic is the set of rules and workflows that define what an application does for its users.
In an online shop, it includes how prices and discounts are calculated, when an order is considered paid, and how many items a customer may buy.
In a bank, it includes who may transfer money, how much, and which approvals are needed.

A business logic flaw lets a user achieve an outcome the business did not intend, using the application's legitimate features.
Examples include buying items for less than their price, redeeming a voucher many times, or approving one's own expense claim.

### Why logic flaws are hard to find

Requests that exploit logic flaws usually look valid.
A negative quantity is a well-formed number, and calling the confirmation step before the payment step is a normal HTTP request.
Generic scanners and input filters look for malicious patterns, such as injection payloads, and cannot know that a request breaks a business rule.
Each application's rules are different, so finding logic flaws requires understanding what the application is supposed to do.

Logic flaws often come from assumptions:

- That users follow the steps in the order the user interface presents them
- That the client sends only the values the user interface allows
- That each user sends one request at a time
- That users will not create many accounts or automate their actions

[CWE-840: Business Logic Errors](https://cwe.mitre.org/data/definitions/840.html) groups many weaknesses of this kind.

### Abuse cases

A use case describes how a legitimate user achieves a goal.
An abuse case describes how someone could misuse the same feature, for example "a customer applies the same discount code to many orders at once."
Writing abuse cases while defining requirements helps teams find logic flaws before they are built.
The [OWASP Abuse Case Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Abuse_Case_Cheat_Sheet.html) describes how to create them, and [Module 1](../01%20-%20Secure%20Design,%20Architecture%20and%20Threat%20Modeling/) covers threat modeling in general.

## Enforcing business rules on the server

### Values the client must not decide

Every business rule must be enforced on the server.
Client-side checks improve usability, but anyone can change what the browser or mobile application sends.

Values that the client must not decide include:

- Prices, totals, taxes, and shipping costs
- Discounts and the conditions under which they apply
- Quantities beyond what the business allows
- Account identifiers that determine who pays or who receives
- Status fields, such as `paid`, `approved`, or `verified`

Calculate these values on the server from authoritative data.
If a cart request contains `{"item": 17, "quantity": 1, "price": 0.01}`, the server should ignore the price, look up item 17's current price, and calculate the total itself.
If a client-supplied value must be carried through several steps, keep it on the server or protect it against modification, and check it again before the final step.

### Business constraints

[Module 4](../04%20-%20Input%20Validation%20and%20Output%20Encoding/) covers validating the format of input.
Business rules add constraints that depend on meaning:

- Ranges: a quantity must be at least 1 and at most the per-order limit
- Sign: transfers and quantities usually must not be negative, because a negative transfer can move money in the opposite direction
- Combinations: a delivery date must be after the order date, and a discount may apply only to certain products
- Time: an offer applies only until its end date, and a booking cannot be changed after a deadline

### Numeric errors

Numeric handling can create logic flaws:

- Integer overflow occurs when a value exceeds the largest number a type can hold and wraps around, for example turning a very large quantity into a negative total.
- Rounding errors can be exploited by repeating many small transactions that each round in the user's favor.
- Floating-point types cannot represent many decimal amounts exactly and are unsuitable for money.
- Currency conversion can be abused if rates or rounding differ between conversions in each direction.

Use types designed for exact decimal amounts, check results against expected ranges, and define rounding rules explicitly.

### Limits

Many businesses limit how often or how much a feature can be used, such as transfers per day, tickets per customer, or redemptions per voucher.
Define these limits per user and across the application, and enforce them on the server.
A limit that exists only in the user interface is not a limit.

## Workflows and state

### Multi-step workflows

Many features span several steps, such as checkout, registration, account recovery, or an approval process.
If each step is a separate request, a user can try to call any step directly.

Common workflow flaws include:

- Calling the order confirmation step without completing payment
- Repeating the final step of a promotion to receive its reward several times
- Changing the cart after payment but before order creation
- Skipping identity verification in an account recovery flow

Track each workflow's progress on the server, for example in the database or the session.
Before processing a step, check that the required previous steps were completed for the same user and the same object.
Do not trust a step number, status, or "verified" flag sent by the client.
[CWE-841: Improper Enforcement of Behavioral Workflow](https://cwe.mitre.org/data/definitions/841.html) describes this weakness.

### State transitions

Business objects move through states.
An order might move from `created` to `paid` to `shipped` to `delivered`, or from `paid` to `refunded`.
Define which transitions are allowed and reject all others.
A request to move a `delivered` order back to `paid`, or to refund an order that was never paid, should fail.

### Repeated requests and expiry

Users double-click buttons, browsers retry requests, and networks deliver messages twice.
An operation such as charging a card or issuing a refund must not happen twice because the same request arrived twice.
Idempotent handling means that repeating a request has the same effect as sending it once, for example by recording a unique identifier for each operation and ignoring duplicates.

Incomplete workflows and time-limited artifacts, such as reservations, discount offers, and confirmation tokens, need expiry.
Without expiry, a user can keep seats reserved indefinitely or use an old offer long after it ended.

### Multi-person approval

Some operations are too risky for one person to perform alone, such as large payments, changes to bank details, or granting administrator access.
Requiring approval by a second person, who must not be the requester, limits both fraud and mistakes.
Check on the server that the approver is a different, authorized user.

## Race conditions in business operations

### How races happen

A race condition occurs when the outcome of an operation depends on the timing of concurrent requests.
Many business operations follow a check-then-act pattern: check that something is allowed, then perform it.
If two requests check at the same time, both may pass before either acts.

Examples include:

- Two simultaneous withdrawals that each see enough balance, leaving the account overdrawn
- Twenty parallel requests that each redeem the same single-use voucher
- Two customers who both buy the last seat because both saw it as available

This is a time-of-check to time-of-use (TOCTOU) flaw.
[CWE-367: Time-of-check Time-of-use (TOCTOU) Race Condition](https://cwe.mitre.org/data/definitions/367.html) describes it.
Attackers can send many requests at almost the same moment, so a narrow timing window is still exploitable.

### Making check and act atomic

The check and the action must happen as one indivisible step.
Common techniques include:

- Conditional updates that check and change in one database statement, such as reducing a balance only if it is large enough
- Unique constraints, such as one redemption record per voucher, that make the database reject duplicates
- Database transactions with an isolation level that prevents the conflicting reads, or with explicit row locks
- Optimistic concurrency control, which stores a version number with each record and rejects an update if the version changed since it was read
- Idempotency keys that let the server recognize and ignore repeated attempts of the same operation

A check in application memory, such as a variable or local lock, does not protect an operation handled by several servers or processes.
The shared data store must enforce the rule.

## Abuse of business features

Features designed to attract or reward customers are frequent targets.

Discounts and coupons:

- Guessable codes, such as `SAVE10` or sequential numbers, can be found by trying many values
- Single-use codes can be reused if redemption is not recorded atomically
- Discounts meant to be exclusive can be combined if the rules are not checked together

Referral and loyalty programs:

- Users create fake or duplicate accounts to collect referral rewards
- Points are earned on orders that are later cancelled or refunded

Reservations and inventory:

- Attackers reserve stock or seats without paying, so legitimate customers cannot buy them
- Partial cancellations or refunds return more value than was paid

Internal or unfinished functions can also bypass rules.
A testing endpoint that creates orders without payment, or an old API version without new checks, gives attackers a shortcut.

Controls include generating codes that are long and random, recording each use atomically, defining which discounts can combine, and limiting rewards per account, payment method, and time period.
Reversing rewards when the underlying order is refunded closes another common gap.

## Automated threats against business flows

### Automation as a threat

Some abuse becomes harmful only at scale.
Buying one ticket is normal, and buying thousands within seconds to resell them is scalping.
Each individual request may be completely valid.

The [OWASP Automated Threats to Web Applications](https://owasp.org/www-project-automated-threats-to-web-applications/) project names common automated threats, including:

- Scalping, buying limited goods to resell them
- Scraping, collecting large amounts of data such as prices or user profiles
- Account creation in bulk, for spam or reward abuse
- Card testing, using small purchases to check which stolen card numbers work
- Credential stuffing, trying stolen username and password pairs on the login page

[Module 2](../02%20-%20Authentication%20and%20Credential%20Management/) covers credential stuffing as an authentication attack.

### Anti-automation controls

No single control stops all automation.
Common controls and their limits include:

- Rate limits per account, device, and network address, which slow attacks but can be spread across many addresses and accounts
- Challenges such as CAPTCHA, which add friction but can be solved by services and can exclude users with disabilities
- Signals such as unusually fast or regular request timing, unusual navigation, and device characteristics, which help identify bots but can produce false positives
- Business controls, such as purchase limits per customer, identity or payment verification, and holding orders for review

Combine controls according to the value of the flow and the cost of false positives.
[Module 13](../13%20-%20API%20and%20Web%20Service%20Security/) covers rate limits and resource consumption limits for APIs, which protect availability rather than business rules.

## Detecting and responding to abuse

Prevention will not catch every logic flaw, so detection matters.
Log business events such as orders, payments, refunds, discount redemptions, and approvals, including who performed them and the outcome.
[Module 7](../07%20-%20Secure%20Logging/) covers secure logging.

Monitor these events for patterns that suggest abuse:

- Many redemptions of one code, or many accounts sharing one payment method
- Orders with totals or quantities outside normal ranges
- Spikes in failed payments, which can indicate card testing
- Many accounts created from the same source in a short time

Reconcile business records regularly, for example by comparing payments received with orders shipped, or stock counts with sales.
Differences can reveal abuse that no single event showed.
When abuse is detected, the response may include blocking accounts, cancelling or reversing operations, and fixing the underlying flaw.

## Testing business logic

Logic flaws are rarely found by automated scanners, so test cases need to come from the business rules themselves.
Useful tests include:

- Changing prices, totals, quantities, and identifiers in requests
- Calling workflow steps out of order, skipping steps, and repeating the final step
- Sending negative numbers, zero, very large values, and unusual combinations of fields
- Sending many identical requests in parallel to single-use or limited operations
- Exceeding per-user and global limits, and checking that the excess is rejected
- Moving objects through state transitions that should not be allowed

Abuse cases written during design make good starting points for these tests.
Manual review by someone who understands the business is often the most effective way to find logic flaws.
The [OWASP Web Security Testing Guide: Business Logic Testing](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/10-Business_Logic_Testing/README) describes test techniques in more detail.

## Reviewing a ticket sales feature

Consider a fictional event ticketing site preparing for a popular concert.
Each customer may buy up to four tickets, and a launch code gives 20 percent off on the first day.
Before the sale opens, the team reviews the checkout with abuse cases in mind.

The cart request includes each ticket's price, and the server uses it to calculate the total.
A test that changes the price to `1.00` creates a valid order.
The team changes the server to look up prices from the event data and ignore prices sent by the client.

The checkout has three steps: select seats, pay, and confirm.
Calling the confirm step directly with a reservation identifier issues tickets without payment.
The team records each reservation's state on the server and allows confirmation only for reservations in the `paid` state that belong to the current customer.

The four-ticket limit is checked by counting existing orders before creating a new one.
A test that sends ten purchase requests in parallel produces ten orders.
The team moves the limit into a single database transaction that locks the customer's order records, and adds the same protection to the launch code, whose redemptions are now recorded with a unique constraint per customer.

Seat reservations never expire, so a script could reserve every seat without paying.
The team releases unpaid reservations after ten minutes and limits how many seats one customer can hold at a time.

Finally, the team expects scalpers to use automated accounts.
They add purchase limits per payment card, a verification step for new accounts, and monitoring for many accounts sharing payment details or network addresses.
Logs of orders, redemptions, and released reservations let them see and respond to abuse during the sale.
