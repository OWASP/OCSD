# Supplementary reading – API and Web Service Security

This chapter covers the risks of APIs and web services and the controls that protect the data and functions they expose.

## APIs and their risks

An application programming interface (API) lets software call functions and exchange data with other software.
Web APIs receive requests over HTTP and return structured data, usually JSON or XML.
A web service is an older term for the same idea, often used for SOAP-based interfaces.

Browsers, mobile applications, partner systems, and internal services all call APIs.
A single-page web application may use the same API as the company's mobile application and its partners.

APIs expose an application's structure more directly than a user interface does.
Requests contain object identifiers such as `/orders/1042`, field names that map to internal data, and endpoints for each business function.
Anyone can send requests directly to an API with a script or a command-line tool.
Hiding a button in the user interface does not prevent a client from calling the endpoint behind it.

The [OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) lists the most common API risks:

- API1 Broken Object Level Authorization
- API2 Broken Authentication
- API3 Broken Object Property Level Authorization
- API4 Unrestricted Resource Consumption
- API5 Broken Function Level Authorization
- API6 Unrestricted Access to Sensitive Business Flows
- API7 Server Side Request Forgery
- API8 Security Misconfiguration
- API9 Improper Inventory Management
- API10 Unsafe Consumption of APIs

Three of the ten are authorization failures.
The following sections cover each risk in the context where it arises.

## Authentication and authorization for APIs

### Authenticating requests

APIs are usually stateless: each request carries what the server needs to authenticate the caller.
Send credentials and tokens in request headers, such as the `Authorization` header.
URLs end up in server logs, proxy logs, browser history, and `Referer` headers, so tokens in query strings are easily exposed.

An API key identifies the calling application, such as a partner's integration.
It does not identify which user is acting, and it is often long-lived and shared across a team.
Use API keys for identifying and limiting client applications, and use user authentication when the API acts on behalf of a user.

Access tokens issued through OAuth 2.0 must be validated on every request.
Validation includes the signature or token status, the issuer, the expiry, and the audience, which states which API the token is meant for.
A token issued for a different API must be rejected even if its signature is valid.
Scopes limit what a token permits, and the API must check that the token has the scope the operation requires.
[Module 2](../02%20-%20Authentication%20and%20Credential%20Management/) covers OAuth 2.0, OpenID Connect, and token validation.

Services that call each other also need authentication.
Common approaches are the OAuth 2.0 client credentials flow, in which a service obtains a token with its own credentials, and mutual TLS, in which both sides present certificates.
[Module 9](../09%20-%20Secure%20Communications/) covers mutual TLS.

### Object-level authorization

Broken object-level authorization (BOLA) occurs when an API returns or changes an object without checking that the caller may access it.
For example, a user requests `GET /api/orders/1043` instead of their own order `1042` and receives another customer's order.
Authentication alone does not prevent this, because the attacker is a legitimate, signed-in user.

Check authorization for every object identifier the API receives.
Identifiers can appear in the path, query string, request body, and headers, and one request may contain several.
Random identifiers make guessing harder but do not replace the check.
[Module 3](../03%20-%20Authorization/) covers authorization models and enforcement.

### Function-level authorization

Broken function-level authorization (BFLA) occurs when a caller can use an operation intended for another role.
A regular user might call `DELETE /api/users/77` or an endpoint under `/api/admin/` because the API checks only that the caller is signed in.
APIs often expose the same resource with several HTTP methods, and each method needs its own authorization rule.

### Property-level authorization

Authorization also applies to individual fields.

Mass assignment occurs when an API copies all fields from a request into an internal object.
A user who sends `{"name": "Ana", "role": "admin"}` to update their profile may change their own role.
Bind only the fields that the operation allows, using an allowlist or a dedicated request object.

Excessive data exposure occurs when an API returns full internal objects and relies on the client to display only some fields.
The hidden fields are still in the response, and anyone can read them.
Return only the fields the client needs and the caller is allowed to see.
The [OWASP Mass Assignment Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Mass_Assignment_Cheat_Sheet.html) describes framework-specific protections.

## Request and response handling

### Validating requests

APIs often have a formal specification, such as an OpenAPI document or a GraphQL schema.
Validate each request against it: types, formats, required fields, and allowed values.
Reject fields the operation does not expect rather than ignoring them, because unexpected fields can reach code that binds them.
[Module 4](../04%20-%20Input%20Validation%20and%20Output%20Encoding/) covers input validation and injection prevention, which apply to API input in the same way.

Check that the request's `Content-Type` header matches a format the endpoint supports, and reject others.
An endpoint that accepts JSON may also parse XML if the framework allows it, which exposes XML parser risks.

Set limits on the size and shape of requests:

- Total request size
- Length of strings and arrays
- Depth of nested objects

Without these limits, a single request can consume large amounts of memory or processing time.

### Parsers and deserialization

Parsers turn request bodies into data structures.
XML parsers that process external entities can read local files or make network requests, as Module 4 describes.
Deserialization features that create arbitrary object types from input can let an attacker run code.
Configure parsers to produce plain data, and disable features the API does not need.
The [OWASP Deserialization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html) covers language-specific risks.

### Responses

Set the correct `Content-Type` on responses, such as `application/json`, so browsers do not interpret them as HTML.
Return generic error messages without stack traces or internal details, as [Module 6](../06%20-%20Error%20Handling/) describes.

### Browser clients

When a web page from one origin calls an API on another origin, the browser applies Cross-Origin Resource Sharing (CORS).
For requests that are not simple, such as those with a JSON body or custom headers, the browser first sends a preflight `OPTIONS` request.
The API's response tells the browser which origins, methods, and headers are allowed.

Preflight checks happen only in browsers.
Other clients send any request they like, so the API must still authenticate and authorize every request.
APIs that rely on cookies for authentication also need protection against cross-site request forgery, because browsers attach cookies automatically to some cross-site requests.
[Module 14](../14%20-%20Secure%20Configuration%20and%20Deployment/) covers CORS configuration mistakes.

## Resource consumption

### Limits

Every API request uses processing time, memory, bandwidth, and sometimes paid services.
Unrestricted resource consumption occurs when an API places no effective limit on these.
The result can be denial of service, in which legitimate users cannot use the application, or unexpected costs.

Controls include:

- Rate limits per client, user, and operation, such as 100 requests per minute
- Quotas over longer periods, such as a daily limit for each API key
- Maximum page sizes for lists, rather than letting the client request all records
- Limits on the number of items in batch operations and on uploaded data
- Timeouts for processing and for calls to other services

Operations that cost money per call need tighter limits.
Examples include sending text messages or emails, charging cards, and calling paid AI models.
An attacker who calls a password reset endpoint in a loop can run up a large messaging bill.

When a request exceeds a limit, return status code 429 Too Many Requests, optionally with a `Retry-After` header that tells clients when to try again.

### Sensitive business flows

Some attacks use each request exactly as intended, but at a scale that harms the business.
Examples include buying an entire stock of limited products with automated scripts or creating thousands of accounts to abuse a referral bonus.
Rate limits help, but these flows also need business-specific protections.
[Module 11](../11%20-%20Business%20Logic%20Security/) covers protecting sensitive business flows.

## API styles

### REST

REST APIs model data as resources identified by URLs and use HTTP methods to act on them.
`GET` reads, `POST` creates, `PUT` and `PATCH` change, and `DELETE` removes.
Authorization rules must cover every method on every resource.
Methods that the API does not support should be rejected.
The [OWASP REST Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html) covers REST-specific guidance.

### GraphQL

GraphQL APIs expose a single endpoint and let clients ask for exactly the data they need in one query.
This flexibility changes where controls belong.

Authorization must be checked in each resolver, the function that fetches a field or object.
A query can reach the same object through several paths, such as `order.customer` and `customer(id: 5)`, and every path needs the check.

Queries can be nested deeply or request very large results.
A query such as users, their friends, those friends' friends, and their posts can multiply into millions of records.
Limit query depth and estimate query cost before running it.

GraphQL allows several operations in one request through batching and aliases.
An attacker can try hundreds of password guesses in one HTTP request, which bypasses rate limits that count requests.
Count operations rather than requests, and limit batch sizes.

Introspection lets clients ask the API for its full schema.
It helps development, but in production it gives attackers a map of every type and field.
Disable it in production unless the API is intentionally public.
The [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html) describes these controls.

### SOAP and XML-based services

SOAP services exchange XML messages.
Harden XML parsers by disabling document type definitions and external entities.
Some SOAP services use WS-Security to sign messages.
A signature protects only the parts of the message it covers, so check that the signed parts are the ones the service acts on.
The [OWASP Web Service Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Web_Service_Security_Cheat_Sheet.html) covers SOAP services.

### gRPC

gRPC is a framework for calls between services that uses compact binary messages.
Protect gRPC connections with TLS, because some setups default to unencrypted connections for internal traffic.
Credentials travel in request metadata, which works like HTTP headers.
Message definitions describe types, but they do not enforce business rules, so validate message content.
Server reflection, like GraphQL introspection, describes every service and method, and it should be disabled in production unless needed.

## Webhooks and outbound requests

### Receiving webhooks

A webhook is an HTTP request that one service sends to a URL registered by another service when an event happens.
For example, a payment provider calls an application's webhook endpoint when a payment succeeds.

A webhook endpoint is reachable from the internet, so anyone can send requests that look like real events.
Verify each webhook before acting on it:

- Check the signature, usually a hash-based message authentication code (HMAC) computed over the request body with a secret shared with the sender
- Compare signatures with a constant-time comparison function
- Reject requests with timestamps outside a short window, which limits replay of captured requests
- Record processed event identifiers and ignore duplicates

Providers may deliver the same event more than once, so process events idempotently: handling an event twice must have the same result as handling it once.
When in doubt, confirm important events, such as payments, by querying the provider's API.

### Server-side request forgery

Some API features fetch a URL supplied by the client, such as importing an image, previewing a link, or registering a webhook destination.
Server-side request forgery (SSRF) occurs when an attacker makes the server request a destination of the attacker's choice.
The server can usually reach systems the attacker cannot, such as internal services, administration interfaces, and cloud metadata services that provide credentials.

SSRF controls include:

- Allowing only destinations on an allowlist when the set of valid destinations is known
- Resolving the host name and rejecting private, loopback, link-local, and metadata addresses
- Checking redirect targets in the same way as the original URL, or not following redirects
- Restricting the server's outbound network access so that only required destinations are reachable

Checking the URL text alone is not enough, because a host name can resolve to an internal address.
The [OWASP Server-Side Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) describes these defenses in detail.
[Module 12](../12%20-%20Secure%20File%20and%20Resource%20Handling/) covers SSRF in file and resource handling.

## Consuming third-party APIs

Applications also call other organizations' APIs, for example to look up addresses, verify identities, or process payments.
Developers often trust these responses more than user input.
An attacker who compromises or impersonates the third party, or who can influence the data it returns, can then attack the application.

Treat third-party responses as untrusted input:

- Validate the response against the expected format before using it
- Encode data from the response for the context where it is displayed or stored
- Use TLS and verify certificates for every call
- Set timeouts and maximum response sizes
- Do not follow redirects blindly, especially to other hosts

Store credentials for third-party APIs in a secret store and request only the permissions the integration needs.
Plan for the third party being slow, unavailable, or returning errors, so that its failure does not leave the application in an unsafe state.

## API inventory and lifecycle

Organizations often lose track of their APIs.
Old versions keep running after a new version is released, test environments remain reachable from the internet, and internal APIs are exposed by mistake.
These forgotten APIs miss security fixes and are attractive targets.

An API inventory records:

- Each API, its versions, and where it is deployed
- Who owns it and who uses it
- The data it handles and the services it calls

API specifications support security review and testing, because they state what each endpoint accepts and returns.
Retire old versions on a schedule and remove them rather than leaving them reachable.
Keep non-production environments away from production data and restrict access to them.

An API gateway sits in front of APIs and can enforce authentication, rate limits, and routing centrally.
It cannot usually decide whether a user may access a specific object, because that requires the application's data.
Object-level and property-level authorization remain the application's responsibility.

## API security testing

Test APIs directly rather than through the user interface.
Useful test cases include:

- Requesting objects that belong to another user, with each HTTP method the API supports
- Calling administrative endpoints with a regular user's token
- Sending extra fields such as `role` or `isAdmin` and checking that they are ignored or rejected
- Checking responses for fields the caller should not see
- Sending wrong types, oversized values, unexpected content types, and deeply nested structures
- Exceeding rate limits, page sizes, and GraphQL query depth or cost limits
- Sending webhooks with missing or invalid signatures and replaying valid ones
- Submitting internal addresses and redirecting URLs to URL-fetching features

An API specification lets tools generate requests for every endpoint, including fuzzing with unexpected input.
Contract tests compare the running API with its specification and detect undocumented endpoints or fields.
The [OWASP Web Security Testing Guide: API Testing](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/12-API_Testing/README) covers API testing techniques.

## Reviewing an order API

Consider a fictional online shop that has added an API for its new mobile application.
Before launch, the team reviews the API with the curriculum's API risks in mind.

The endpoint `GET /api/v2/orders/{id}` checks that the user is signed in and returns the order.
It does not check that the order belongs to the user.
The team adds an object-level authorization check and a test that requests another user's order and expects a denial.

The profile update endpoint binds the whole request body to the user object.
A test that sends `"role": "admin"` succeeds in changing the role.
The team replaces the binding with a request object that contains only the name, address, and phone number fields.

The order list returns full order objects, including internal fraud scores, and the mobile application hides them.
The team returns a smaller response containing only the fields the application displays.

The order list also accepts any page size, and a request for one million orders slows the database for everyone.
The team sets a maximum page size of 100 and adds rate limits per user.

The payment provider's webhook endpoint marks orders as paid without verifying the request.
Anyone who knows the URL could mark an unpaid order as paid.
The team verifies the provider's signature and timestamp, records event identifiers to ignore duplicates, and confirms payments with the provider's API before shipping.

Finally, the inventory review finds that `/api/v1/`, used by an old version of the website, is still reachable and lacks the new checks.
The team moves the remaining website features to version 2 and removes version 1.

The team adds the new tests to the pipeline so these checks run on every release.
