# Supplementary reading – Secure Communications

## What TLS protects

Transport Layer Security (TLS) protects data as it travels between two endpoints, such as a browser and a web server.
It keeps the data private, detects tampering, and lets the client verify the server's identity.
For example, TLS helps prevent someone who can observe network traffic from reading a session cookie or changing a response on its way to the browser.

A reverse proxy accepts requests on behalf of an application and forwards them to it.
When the proxy terminates TLS, it acts as the endpoint of the client's connection and can read the decrypted request.
The proxy forwards the request over a separate connection to the application.
If this connection uses unencrypted Hypertext Transfer Protocol (HTTP), anyone who can observe traffic on that link can read the forwarded data.
Use a protected connection and verify the intended peer on internal links as well as on public ones.
Each endpoint remains responsible for protecting the data it handles and enforcing its own access rules.

## TLS versions and downgrade prevention

Use a maintained TLS library, framework, or managed service and check its configuration for each endpoint.
Prefer TLS 1.3.
Enable TLS 1.2 only where compatibility requires it.
Keep TLS 1.0, TLS 1.1, and the older Secure Sockets Layer (SSL) protocols disabled.

The client and server negotiate settings they both support during the TLS handshake, the exchange that sets up the connection.
A downgrade attack tries to make them use weaker settings.
TLS 1.3 includes downgrade protections, and the deployment's allowed settings determine which connections it will accept.
For example, a client that supports only TLS 1.2 can connect to a server that permits it for compatibility.
If the peers share no acceptable settings, the connection should fail.
Keep the same security requirements on every retry.

### Cipher suites and forward secrecy

A cipher suite is a named set of algorithms that determines how TLS protects traffic.
In TLS 1.2, the suite also specifies how the client and server establish the keys for the connection.
It can also specify how the server proves its identity.
In TLS 1.3, the client and server make those choices separately during the handshake.

The cipher suites defined in the TLS 1.3 specification all encrypt traffic and detect tampering.
TLS 1.2 offers some of the same encryption algorithms in suites designed for that version.
Choose a TLS 1.2 suite that provides both protections, authenticates the server, and uses temporary keys to agree on a shared secret.

Suppose someone records encrypted traffic and later steals the server's long-term private key.
If the client and server used temporary keys to agree on a shared secret, the stolen private key alone cannot decrypt the recording.
This protection is called forward secrecy.
Some older TLS 1.2 suites let the server use its long-term private key to recover the connection secret.
Anyone with that key and a recording of the handshake can then recover the same secret.

Session resumption lets a client and server reconnect using a secret established by an earlier connection.
In TLS 1.3, they can also use fresh temporary keys to agree on a new shared secret when they reconnect.
This protects traffic sent after the handshake if someone later steals the secret used to resume the session.
If the resumed connection relies on that earlier secret alone, someone who steals it can decrypt recorded traffic from the resumed connection.
See [Module 5's key agreement and public-key trust section](../05%20-%20Cryptography%20and%20Key%20Management/05.03%20-%20Supplementary%20Reading%20Materials.md#key-agreement-and-public-key-trust) for the cryptography behind TLS.

## Certificate trust and lifecycle

A certificate binds a public key to an identity, such as a service's domain name.
A certificate authority (CA) signs the certificate to vouch for that binding.
A chain of certificates links the service certificate to an authority the client trusts.

The client verifies the chain, checks that the certificate is currently valid, and matches the expected service name against a name in the certificate's Subject Alternative Name field.
The expected name comes from the address the client intended to contact.
The TLS handshake also verifies that the server holds the private key associated with the certificate.
A public website uses a certificate that browsers can verify through their public trust settings.
An internal service can use a private CA when its clients are configured to trust that specific authority.

When verification fails, stop the request and correct the cause before reconnecting.
For example, replace an expired certificate, correct a wrong service address, or restore a missing certificate in the chain.
If the service intentionally uses a private CA, obtain the correct CA certificate through an approved source before updating the client's trust settings.
Keep certificate and service-name verification enabled in development and production.

Limit certificates to the names their service needs, and restrict access to the corresponding private keys.
Automate renewal where possible and monitor the certificates actually served by your endpoints.
A renewed certificate must be deployed before the old one expires, including at proxies that terminate TLS.
If a private key is compromised, deploy a replacement certificate with a new key and arrange for the old certificate to be revoked.

### Pinning and certificate transparency

Some teams that control both the client and the service use certificate pinning to require a particular certificate or public key in addition to the usual verification checks.
Pinning limits which certificates the client will accept and can cause an outage when a certificate or key changes.
Treat a pin mismatch as a failed connection and investigate through a trusted channel before updating the pin.

Certificate Transparency uses public logs of issued certificates that domain owners can monitor for unexpected issuance.
Some browsers require evidence of logging for publicly trusted server certificates.

## Mutual TLS and service identity

With server-authenticated TLS, the client verifies the server's identity.
Mutual TLS (mTLS) adds a client certificate so the server can also verify the client.
For example, an internal service can verify the certificate of the worker that calls it.
The worker's verified identity is one input when the application decides whether to allow a requested operation.

Some teams use a service mesh, infrastructure that manages traffic among services, to set up and enforce mTLS.
Check which links the mesh protects and where the connections terminate.
When a proxy opens a new mTLS connection with its own client certificate, that certificate identifies the proxy to the receiving service.

## HTTPS in browsers

HTTPS uses TLS to protect HTTP traffic.
When a site redirects a browser from HTTP to HTTPS, the browser makes a new request over TLS after the original request has crossed the network unencrypted.
Configure service clients to use HTTPS directly and reject redirects to HTTP.

HTTP Strict Transport Security (HSTS) lets a site tell browsers to use HTTPS for future requests.
A browser can learn the policy from the `Strict-Transport-Security` header in a valid HTTPS response.
The `max-age` directive specifies how long the browser remembers the policy, in seconds.
The `includeSubDomains` directive extends the policy to subdomains, so check that they support HTTPS before enabling it.
When a browser already knows the policy, it upgrades HTTP URLs for that host before sending the request and refuses to proceed if certificate verification fails.

A browser that has no HSTS policy for the host can send its first request over HTTP.
A preload list can provide that policy before the browser receives an HTTPS response from the site.
Joining the list is optional and requires a separate submission and a commitment to keeping the domain and its subdomains accessible over HTTPS.

### Mixed content and browser controls

Mixed content occurs when an HTTPS page tries to load a resource over an insecure connection.
For example, an insecure script could be modified in transit and run with the page's privileges if the browser loaded it.
Browsers block some insecure requests and upgrade others, such as requests for certain images.
Use HTTPS resource URLs and check that the resources are available over HTTPS.

Content Security Policy (CSP) lets a site set browser rules for what a page can load and where it can connect.
The `upgrade-insecure-requests` directive tells the browser to try secure URLs for eligible insecure requests made by the page.
If a resource cannot be reached securely, the upgraded request fails.
The `connect-src` directive restricts destinations for connections initiated by page scripts, including requests to application programming interfaces (APIs) and WebSocket connections.
A backend service that calls the same API relies on its own TLS settings.

Set the `Secure` attribute on session cookies and prefix their names with `__Secure-` or `__Host-` so browsers send them only over HTTPS.
See [Module 2's guidance on protecting session tokens](../02%20-%20Authentication%20and%20Credential%20Management/02.03%20-%20Supplementary%20Reading%20Material.md#protecting-session-tokens) for other cookie attributes and session safeguards.

## Secure WebSockets

A WebSocket lets the client and server exchange messages over an ongoing connection.
Use `wss://` so TLS protects the opening handshake and subsequent messages.
A connection using `ws://` lacks that protection.

Check the browser's `Origin` header against the origins allowed to open a WebSocket before accepting the connection.
The origin identifies the scheme, host, and port of the page opening the connection.
This check helps prevent another site from opening a socket that uses the user's existing session cookie.
A client outside the browser can supply any `Origin` value.
Authenticate the client before processing protected messages.

For a socket tied to a login session, close the connection when the session expires or is revoked.
Authorize each requested action against the resource it targets, even if the client was allowed to open the socket.
Validate the type, structure, and size of incoming messages before acting on them.
Limit open connections and message rates, and close idle connections to protect server resources.

## Reviewing the connections in a support application

A support application displays delivery status from an external carrier API.
The browser connects to `support.example.com` over HTTPS and verifies the proxy's certificate for that name.
The proxy terminates TLS so it can read and route the request.
The proxy currently forwards requests over HTTP, which exposes the forwarded session cookie and request contents on the internal network.

The team changes the link from the proxy to the application to use mTLS.
The proxy verifies the application's certificate for `support.internal.example.com` using the approved internal CA.
The application verifies the proxy's client certificate and allows the verified proxy identity to forward requests.
The application still checks the user's session and permission to view the order.

On the outbound connection, the application is the TLS client and verifies the carrier's certificate for `api.carrier.example`.
If the carrier presents a certificate for a different name, the application stops before sending the API request or its credentials.
It shows the user that delivery status is temporarily unavailable and logs the verification failure without recording credentials.
The team checks the configured address and the certificate presented by the carrier, and traffic resumes over verified HTTPS when the cause is fixed.

## Additional learning resources

- [RFC 9846 – The Transport Layer Security (TLS) Protocol Version 1.3](https://www.rfc-editor.org/rfc/rfc9846.html) specifies TLS 1.3 and describes its handshake and cryptographic negotiation
- [RFC 9325 – Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)](https://www.rfc-editor.org/rfc/rfc9325.html) provides deployment guidance, including for TLS 1.2
- [RFC 9525 – Service Identity in TLS](https://www.rfc-editor.org/rfc/rfc9525.html) describes how clients verify the identity of the intended service
- [RFC 8555 – Automatic Certificate Management Environment (ACME)](https://www.rfc-editor.org/rfc/rfc8555.html) specifies a protocol used to automate certificate issuance
- [Chrome Certificate Transparency Policy](https://googlechrome.github.io/CertificateTransparency/ct_policy.html) describes one browser's requirements for evidence of logging
- [RFC 6797 – HTTP Strict Transport Security (HSTS)](https://www.rfc-editor.org/rfc/rfc6797.html) defines the HSTS policy and browser behavior
- [HSTS Preload List Submission](https://hstspreload.org/) describes first-visit protection and the implications of joining the preload list
- [W3C Mixed Content](https://www.w3.org/TR/mixed-content/) defines which insecure requests browsers upgrade or block
- [W3C Upgrade Insecure Requests](https://www.w3.org/TR/upgrade-insecure-requests/) describes the policy for upgrading resource requests
- [W3C Content Security Policy Level 3](https://www.w3.org/TR/CSP3/#directive-connect-src) defines the `connect-src` directive
- [RFC 6455 – The WebSocket Protocol](https://www.rfc-editor.org/rfc/rfc6455.html) defines WebSocket connections and the browser origin check
