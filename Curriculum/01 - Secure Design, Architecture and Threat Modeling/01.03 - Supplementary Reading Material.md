# Supplementary reading – Security Architecture and Threat Modeling

This chapter explains how developers apply security architecture and threat modeling during development.

## Security in the software development lifecycle

Security decisions occur throughout the software development lifecycle.

- Requirements identify what the application must protect.
- Architecture defines components, connections, and control locations.
- Implementation turns the design and its security requirements into software.
- Verification checks whether the controls work as intended.
- Maintenance keeps assumptions, dependencies, and controls current.
- Retirement removes access, data, credentials, and services that are no longer needed.

Teams derive security requirements from risks, policies, standards, and applicable obligations.

Security activities apply to any lifecycle model and fit the team's development process.
During backlog refinement, teams define security requirements.
Design changes trigger reviews of relevant threats and assumptions.
Release criteria include tests for agreed mitigations.

Developers contribute by questioning unclear security assumptions.
They implement assigned controls and report constraints or residual risks.

The [OWASP Secure Product Design Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Product_Design_Cheat_Sheet.html) describes security decisions during product inception and design.
The [OWASP Developer Guide](https://devguide.owasp.org/en/04-design/01-threat-modeling/) explains why identifying threats during design can reduce later rework.

## Security architecture

Security architecture describes how a system's structure supports its security goals.
It includes components, connections, data stores, external services, and security controls.
Architecture documentation records assumptions about users, identities, networks, dependencies, and deployment.

Developers need enough context to answer basic questions about a design:

- What valuable data, operations, or services must the application protect?
- Which components process or store those assets?
- How does data move between components?
- Where does data or control cross a trust boundary?
- Which component makes each security decision?
- Which assumptions would create risk if they were wrong?

A simple data flow diagram can provide this context.
It shows processes, data stores, external entities, and the data that moves between them.
The diagram should also identify relevant trust boundaries.

A trust boundary is a place where the level of trust changes.
Examples include a client application calling a service interface.
Other examples include an application calling a third-party service.
A process reading data from a user-controlled file also crosses a trust boundary.

Security controls belong at reliable enforcement points.
Client-side checks can improve usability.
The receiving application component treats client input as untrusted and enforces security decisions.
The same reasoning applies when one service receives data from another service.

Useful architecture documentation is current, focused, and easy to maintain.
A simple diagram can be sufficient when it shows relevant boundaries and assumptions.

## Essential secure design principles

Secure design principles help developers review choices before and during implementation.
Specific requirements and threat models turn these principles into system behavior.

**Secure by default** means that a new or reset system begins in a restrictive state.
Sensitive access or functionality requires an explicit decision to enable it.

**Minimize the attack surface** means removing unnecessary ways to interact with the system.
This includes unused endpoints, excessive permissions, unneeded services, and avoidable dependencies.

**Least privilege** limits each user, service, and process to the access it needs.
The access should also last no longer than necessary.

**Separation of duties** prevents one person or role from controlling every part of a sensitive operation.
For example, a payment system may separate the ability to create a payment from the ability to approve it.

**Defense in depth** uses complementary controls.
The failure of one control should not expose the entire system.
For example, hiding an administrative action in the user interface can improve usability.
The server protects the action by rejecting requests from users without the required permission.

**Complete mediation** requires the system to check each access to a protected resource.
Every decision uses the current identity, action, resource, policy, and context.

**Fail securely** preserves restrictions when an error occurs.
When a policy service is unavailable, the application denies requests it cannot authorize.

**Simple and reviewable design** reduces mistakes and hidden behavior.
Small, well-understood mechanisms make security behavior easier to review.

## Participating in threat modeling

Threat modeling is a structured discussion about the security of a system or change.
It helps a team make assumptions visible and find design risks before release.
Developers contribute knowledge about implementation details, data flows, and dependencies.

The [OWASP Threat Modeling Project](https://owasp.org/www-project-threat-modeling/) presents the Four Question Framework as a methodology-neutral starting point:

1. What are we working on?
2. What can go wrong?
3. What are we going to do about it?
4. Did we do a good enough job?

The first question defines the scope and creates a shared model of the system.
The model identifies assets, users, components, data flows, and trust boundaries.
It also records dependencies and important assumptions.

The second question identifies threats in that context.
Threat modeling uses several related terms:

- Asset, data, functionality, or another resource that has value
- Threat, a possible event or action that could cause harm
- Vulnerability, a weakness that could allow that harm to occur
- Risk, possible harm in context, including its likelihood and impact
- Control, a safeguard that protects an asset or supports a security objective
- Mitigation, an action that avoids a risk or reduces its likelihood or impact
- Residual risk, the risk that remains after the selected response

STRIDE is one prompt that can help a team find threats systematically.
Its categories prompt the team to consider:

- Spoofing, in which an entity pretends to be another entity
- Tampering, in which data or code is changed without authorization
- Repudiation, in which someone disputes an action when evidence is inadequate
- Information disclosure, in which information is exposed without authorization
- Denial of service, in which a resource becomes unavailable when it is needed
- Elevation of privilege, in which an entity gains unauthorized capabilities

The categories help in structuring the discussion.
The team applies engineering judgment to the results.
The [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html) provides examples of this approach.

The third question selects a response for each relevant risk.
A team can avoid a risk by changing the design.
It can mitigate a risk by adding or improving controls.
An authorized decision-maker can accept or transfer a risk when appropriate.
Developers provide the technical evidence needed for that decision.

The fourth question checks the quality and completeness of the work.
The team reviews assumptions, verifies mitigations, and records unresolved risks.
Threat models must be revisited when important parts of the system change.

## Turning threat-modeling results into requirements and tests

Consider an application that lets a signed-in user change an account email address.
The account and its verified contact details are assets.
The client application, account service, identity service, data store, and email service are components.
Requests to the account service and calls to the email service cross trust boundaries.

One threat is that an attacker with an unattended session changes the email address.
Another threat is that a user changes the address on a different user's account.
The team decides to require recent authentication and authorization at the account service.

Those decisions need specific requirements.
For example, the application must require recent authentication before changing an email address.
It must also authorize the operation for the account associated with the authenticated identity.

The requirements then produce tests.
One test verifies that the application rejects the change without recent authentication.
Another verifies that changing an account identifier cannot target another user's account.
The team can trace the threat to the requirements, implementation, tests, and final decision.

The [OWASP Application Security Verification Standard](https://owasp.org/www-project-application-security-verification-standard/) provides testable application security requirements.
ASVS focuses on web applications and services.
Many ASVS requirements describe controls that also apply to other application types.
Teams select requirements that fit the application's architecture and risk context.
