# Supplementary reading – Secure File and Resource Handling

This chapter covers accepting, storing, processing, and serving files safely, and accessing files and resources identified by user input.

## File handling risks

Many applications handle files.
Users upload profile pictures and documents, download invoices and reports, import spreadsheets, and ask the application to fetch images from URLs.
Each of these features gives an attacker a way to place data on the server or to influence which file the server reads.

Unsafe file handling can lead to:

- Server-side code execution, when an uploaded file is run as a script
- Cross-site scripting, when an uploaded HTML or SVG file is served from the application's origin and opened in a browser
- Unauthorized access, when a user downloads another user's files or the server reads files outside the intended directory
- Malware distribution, when the application stores and serves malicious files to other users
- Denial of service, when large or specially crafted files exhaust disk space, memory, or processing time

Treat every part of a file as untrusted input: its name, its path, its declared type, its size, and its contents.
[Module 4](../04%20-%20Input%20Validation%20and%20Output%20Encoding/) covers handling untrusted input in general.

## Validating uploaded files

### File types

Define which file types each upload feature accepts, and reject everything else.
A profile picture feature might accept only JPEG and PNG images.
An allowlist like this is easier to get right than a list of forbidden types, because new dangerous types keep appearing.

The client controls the file name and the `Content-Type` header of an upload.
A file named `photo.jpg` with the header `Content-Type: image/jpeg` can contain anything.
Check the extension against the allowlist, and then check the content.

Many file formats start with a recognizable byte sequence, called a file signature or magic number.
PNG files, for example, start with the bytes `89 50 4E 47`.
Checking the signature confirms that the content plausibly matches the type.

Type checks have limits.
A polyglot file is valid in more than one format, such as a file that is both a valid image and a valid script.
Signature checks look only at the start of the file and cannot detect content hidden elsewhere.
Type checks are therefore one layer, combined with safe storage and serving.

### Size and quantity

Set limits on:

- The size of each file and of the whole request
- The number of files per request and per user
- The total storage each user can consume
- Image dimensions, because a small compressed image can expand to an enormous number of pixels in memory

Enforce limits as early as possible, before reading the whole upload into memory.

### File names

Client-supplied file names can contain path separators, `../` sequences, control characters, or names that clash with existing files.
Generate a new name for each stored file, such as a random identifier, and record the original name separately if it needs to be shown.
This prevents both path manipulation and overwriting other files.

### Active content

Some file types can contain content that runs when the file is opened:

- Office documents can contain macros.
- SVG images are XML documents that can contain scripts.
- PDF files can contain scripts and links.
- HTML files run scripts when opened in a browser.

Spreadsheet applications treat cells that start with characters such as `=`, `+`, `-`, or `@` as formulas.
When an application exports user-supplied data to a CSV file, a value such as `=HYPERLINK(...)` can run as a formula in the recipient's spreadsheet.
This is called CSV injection or formula injection.
The [OWASP CSV Injection](https://owasp.org/www-community/attacks/CSV_Injection) page describes how to neutralize such values.

Rewriting a file into a safe form removes many hidden threats.
For images, decoding and re-encoding the image produces a new file without extra data or scripts.
Content disarm tools do the same for documents by rebuilding them without active content.

## Storing uploaded files

### Location and execution

Do not store uploaded files in a directory the web server serves directly.
If an attacker uploads `shell.php` into such a directory and the server is configured to run PHP files, requesting the file runs the attacker's code.
[CWE-434: Unrestricted Upload of File with Dangerous Type](https://cwe.mitre.org/data/definitions/434.html) describes this weakness.

Safer options include:

- A directory outside the web root, served only through application code that checks authorization
- Object storage, such as a cloud storage bucket, that never executes stored files
- A separate site, with its own registrable domain, used only for user content

If uploaded files must sit under the web server, configure that directory so nothing in it can run.
[Module 14](../14%20-%20Secure%20Configuration%20and%20Deployment/) covers web server configuration.

### Access control

Record which user or resource each stored file belongs to, and check authorization on every access.
Random file names make guessing harder but are not access control.
[Module 3](../03%20-%20Authorization/) covers authorization.

Cloud storage buckets have their own access settings.
A bucket configured for public access exposes every file in it to anyone who knows or guesses the address.
Keep buckets private and give access through the application or through signed URLs, described below.

### Malware scanning

Files that other users will download should be scanned for known malware.
Hold new files in a quarantine area until the scan completes, and make them available only after they pass.
Signature-based scanners recognize known malware and miss new or modified samples, so scanning complements the other controls rather than replacing them.

### Retention

Delete uploaded files when they are no longer needed, including files from abandoned uploads and deleted accounts.
Stored files may contain personal data, and [Module 8](../08%20-%20Data%20Protection%20and%20Privacy/) covers data retention.

## Serving files to users

### Authorization and headers

Check that the requester may access the file on every download.
A download endpoint such as `/files/9876` is an object reference, and missing checks let users read each other's files.

Response headers control how the browser treats a file:

- `Content-Type` should state the file's actual type, determined by the application rather than taken from the upload.
- `X-Content-Type-Options: nosniff` stops the browser from guessing a different type from the content.
- `Content-Disposition: attachment` tells the browser to download the file rather than display it.
- `Cache-Control: no-store` prevents browsers and shared caches from keeping copies of sensitive files.

When the file name appears in `Content-Disposition`, encode it so that characters such as quotes or line breaks cannot change the header.

### Separate site for user content

If an uploaded HTML or SVG file is served from the application's own origin and the browser renders it, its scripts run with access to the application.
Serving user content from a separate site, such as `example-usercontent.com` for an application at `app.example.com`, means such scripts cannot read the application's cookies or data.

A different port or a subdomain such as `files.app.example.com` is not enough.
Cookies are not separated by port, cookies set for a parent domain are sent to its subdomains, and browsers treat subdomains of the same registrable domain as the same site.
Combine a separate site with `Content-Disposition: attachment` and accurate content types.

### Signed URLs

Cloud storage services can generate signed URLs, which grant access to one object for a limited time.
The application checks authorization and then gives the user a signed URL instead of streaming the file itself.
Keep the lifetime short and limit the URL to one object and one operation.
Anyone who obtains a signed URL can use it until it expires, so treat it like a temporary credential.

Signed URLs can also let users upload directly to storage.
Restrict them to an expected object name, content type, and maximum size, and validate the uploaded file before the application uses it.

## File paths from user input

### Path traversal

Path traversal occurs when user input changes which file the application reads or writes.
Consider a download feature that builds the path `/var/app/reports/` + `name`.
A request with `name=../../../etc/passwd` produces `/var/app/reports/../../../etc/passwd`, which the operating system resolves to `/etc/passwd`.
[CWE-22: Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal')](https://cwe.mitre.org/data/definitions/22.html) describes this weakness.

Attackers vary the input to avoid simple filters:

- Absolute paths, such as `/etc/passwd`
- Encoded sequences, such as `%2e%2e%2f` or double encoding
- Alternative separators, such as `..\` on Windows
- Nested sequences, such as `....//`, which become `../` after a filter removes `../` once
- Null bytes, such as `../../etc/passwd%00.jpg`, which some older runtimes and native file functions treat as the end of the path after an extension check has passed

Removing `../` from input therefore does not reliably prevent traversal.

### Defenses

The best defense avoids user-supplied paths altogether.
Give each file an identifier, store the mapping from identifier to file path on the server, and accept only the identifier.

When a user-supplied name is unavoidable:

1. Validate it against an allowlist of characters or names.
2. Combine it with the base directory.
3. Canonicalize the result, which resolves `.`, `..`, and symbolic links into a single absolute path.
4. Canonicalize the base directory in the same way.
5. Check that the canonical path is inside the canonical base directory by comparing path components.

Symbolic links can point outside the base directory, which is why the check uses the resolved path.
A plain string comparison is not enough.
If the base directory is `/var/app/reports`, the path `/var/app/reports2/secret` starts with the same text but lies outside it.
Use the language's path functions that compare whole directory components, or compare against the base directory followed by a path separator.
Running the application with file system permissions limited to the directories it needs reduces the damage if a check fails.

## Archives and file processing

### Archive extraction

Archives such as ZIP and TAR files contain entries with their own names and paths.
Zip Slip occurs when an extraction routine writes each entry to the path given in its name.
An entry named `../../app/config.php` is then written outside the extraction directory, possibly overwriting application code.
Apply the path checks above to every entry before writing it.
Archives can also contain symbolic links that point elsewhere on the server, so reject them unless the feature requires them.

A decompression bomb is a small archive that expands to a huge size, for example a few kilobytes that expand to many gigabytes.
Limit the total uncompressed size, the number of entries, and the depth of nested archives, and stop extraction when a limit is reached.
[CWE-409: Improper Handling of Highly Compressed Data (Data Amplification)](https://cwe.mitre.org/data/definitions/409.html) describes this weakness.

### Parsers and converters

Image, document, and media libraries parse complex formats and have a history of serious vulnerabilities.
A crafted image can trigger a flaw in an image library and run code on the server.
Keep these libraries updated, enable only the formats the feature needs, and process untrusted files in an isolated environment with memory, CPU, and time limits.

Many formats are XML underneath, including office documents and SVG images.
Parsers that process external entities in these files can read local files or make network requests.
Module 4 covers XML external entity prevention.

## File inclusion and dynamic loading

Some languages and frameworks can load and run code or templates from a file chosen at runtime.
Local file inclusion occurs when user input selects which local file is loaded, for example `?page=../../uploads/shell.txt`.
Remote file inclusion occurs when the input can name a file on another server, which the application then downloads and runs.
[CWE-98](https://cwe.mitre.org/data/definitions/98.html) describes this weakness in PHP, where it is most common.

Map user choices to a fixed list of files, such as `{"about": "about.html", "help": "help.html"}`, and reject anything else.
Disable language features that allow including remote files.

## Fetching remote resources

Features such as "import image from URL" or "preview this link" make the server fetch a resource from a user-supplied URL.
Server-side request forgery (SSRF) occurs when an attacker uses such a feature to make the server request internal systems, administration interfaces, or cloud metadata services.

For file-fetching features:

- Allow only the URL schemes the feature needs, usually `https`, and reject schemes such as `file:` that read local files
- Apply destination allowlists and block internal and metadata addresses, connecting only to the address that was checked
- Check redirect targets in the same way, or do not follow redirects
- Limit the response size and the time allowed for the fetch
- Validate the fetched content in the same way as an upload

Connecting to the checked address matters because of DNS rebinding.
An attacker who controls a host name's DNS records can return a public address when the application checks the name and an internal address when it connects.
[Module 13](../13%20-%20API%20and%20Web%20Service%20Security/) covers SSRF controls in more detail.

## Temporary files and race conditions

Applications create temporary files while processing uploads, generating reports, or converting formats.
Temporary directories are often shared with other programs and users on the same system.

Use library functions that create the temporary file itself, with an unpredictable name and only if it does not already exist, so another process cannot create or replace it first.
Avoid older functions that only return a name for the caller to open later, such as C `tmpnam` and `mktemp` or Python `tempfile.mktemp`, because the file can be created by someone else in between.
Predictable names such as `/tmp/report-1234.pdf` let an attacker create a file or link with that name in advance.
Give temporary files restrictive permissions and delete them after use, including when processing fails.

A time-of-check to time-of-use (TOCTOU) race condition occurs when a program checks a file and later uses it, and the file changes in between.
For example, an application checks that a path is not a symbolic link and then opens it, while an attacker replaces it with a link between the two steps.
Prefer operations that check and act in one step, such as opening a file with options that refuse to follow links, and then working with the open file.

## Testing file handling

Useful tests include:

- Uploading files with disallowed extensions, double extensions such as `photo.jpg.php`, and mismatched content types
- Uploading files that are valid in two formats, such as an image that also contains a script
- Uploading files and archives that exceed size, count, dimension, and compression limits
- Uploading archives with entries such as `../../evil.txt` and with symbolic links
- Requesting files with path traversal sequences and their encoded variants
- Requesting another user's files through download endpoints and signed URLs
- Requesting uploaded files directly to check that they are not executed and are served with safe headers
- Submitting internal addresses and `file:` URLs to URL-fetching features

The [OWASP Web Security Testing Guide: Test Upload of Malicious Files](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/10-Business_Logic_Testing/09-Test_Upload_of_Malicious_Files) describes upload testing in more detail.

## Reviewing a document sharing feature

Consider a fictional project management application in which team members upload attachments to tasks.
Users can also upload a ZIP file to import several attachments at once and set a profile picture from a URL.

The review starts with attachments.
They are saved under their original names in `/public/uploads/`, which the web server serves directly.
A test upload of `notes.php` runs as code when requested.
The team moves attachments to a private storage bucket, stores them under random identifiers, and records the original names in the database.
Downloads now go through an endpoint that checks the user's access to the task and returns a short-lived signed URL.

An uploaded HTML attachment opens in the browser and its script runs on the application's domain.
The team serves attachments from a separate user-content site with `Content-Disposition: attachment`, accurate content types, and `X-Content-Type-Options: nosniff`.
New attachments stay in quarantine until a malware scan completes.

The ZIP import extracts each entry to the path in its name.
A test archive with an entry named `../../app/config.php` overwrites the application's configuration file outside the import directory.
The team checks the canonical path of every entry against the import directory, rejects symbolic links, and limits the total uncompressed size and number of entries.

The profile picture feature fetches any URL the user enters.
A test with `http://169.254.169.254/` returns the cloud metadata service's response.
The team restricts the feature to `https` URLs, blocks internal and metadata addresses, connects only to the checked address, and re-encodes the fetched image before storing it.

The team adds each test to the automated test suite so the checks run on every release.
