# Module 16 – Secure Developer Environment and Security Awareness

This outline defines the developer environment and security awareness knowledge assessed in Module 16.

## 16.1 Threats to development environments

- Why developer workstations hold broader access than typical office endpoints
- Assets in a development environment: source code, credentials, signing keys, cloud and cluster configuration, build settings, test data, and authenticated sessions
- How a compromised workstation can lead to changed source code, stolen credentials, access to internal systems, or a compromised release
- Common entry points: malicious packages and extensions, untrusted repositories, phishing, exposed secrets, unsafe online tools, and lost devices

## 16.2 Workstation protection

- Least privilege for daily work and the risk of routinely using administrator or root accounts
- Separation of development, test, and production access, and of work and personal activity
- Defense in depth on a workstation: disk encryption, screen locking, endpoint protection, host firewalls, and timely updates
- Removal of unneeded software, accounts, and services to reduce the attack surface
- Physical protection of devices and hardware security keys, and exposure of sensitive information during screen sharing

## 16.3 Policies and responsibilities

- Policy topics that affect developers: acceptable use, software installation, approved tools and services, data classification and handling, production access, and remote work
- Why production access should be limited in time and scope, and logged
- Shared responsibility between developers, managers, security teams, and IT for workstation security
- Events that developers report: lost devices, exposed secrets, suspicious software, unexpected sign-in or MFA prompts, and data sent to an unapproved service
- Why prompt reporting limits damage, and why working around a control is not a substitute for raising a concern

## 16.4 Local development tools

- Access that IDEs, editors, extensions, language servers, and command-line tools have to files, terminals, credentials, and the network
- Repository content that can run code when a project is opened, built, or tested: task definitions, workspace settings, build scripts, Git hooks, and package installation scripts
- Workspace trust and restricted modes for unfamiliar repositories
- Trust decisions for extensions and tools: publisher identity, requested permissions, maintenance, and organizational allowlists
- Risks of running downloaded scripts without review, including piping remote content directly into a shell
- Removal of unused extensions and globally installed tools

## 16.5 Online services and code assistants

- How online formatters, converters, decoders, paste sites, and debugging services can retain, publish, or reuse submitted data
- Information that must not be submitted to unapproved services: secrets, tokens, session data, proprietary code, personal data, and internal configuration or security details
- Organizational approval and data handling terms as conditions for using a third-party service
- Local tools, approved services, and sanitized inputs as safer alternatives
- Risks of code assistants: disclosure of submitted code and data, and generated code, commands, or dependencies that need review before use
- The developer's responsibility for code, commands, and dependencies regardless of how they were produced

## 16.6 Secrets and sensitive data

- Types of secrets in development: passwords, API keys, access tokens, private keys, cloud and cluster credentials, and session cookies
- Why secrets do not belong in source code, configuration templates, documentation, or images
- Approved secret stores as an alternative to hardcoded values and shared local files
- Ignored local environment files and committed examples containing placeholder values only
- Scoped, short-lived credentials and the reduced impact of their exposure
- Why a committed secret remains in repository history and must be treated as exposed
- Revoking or rotating an exposed secret, removing it from the current code, and reporting it
- Secret detection before commit and in shared repositories, and the limits of pattern-based detection
- Synthetic or anonymized test data in place of production data
- Removal of secrets and personal data from logs, screenshots, and diagnostic information before sharing

## 16.7 Networks, remote access, and local services

- Risks of home, shared, and public networks, and basic home network protections
- Approved remote access mechanisms and why unofficial tunnels or shared access credentials bypass security controls
- Protection of SSH private keys, host key warnings, and the risks of agent forwarding
- Binding local development services, databases, and dashboards to the local machine unless other access is required
- Authentication, credentials, and lifetime of local development services
- Risks of publicly exposing a development service through tunnels or port forwarding

## 16.8 Containers, virtual machines, and managed workspaces

- Isolation benefits and limits of containers, virtual machines, development containers, and cloud workspaces
- Configurations that weaken container isolation: privileged mode, broad host mounts, a mounted container runtime socket, and unnecessary root execution
- Trusted image sources and secrets stored in images or image build files
- Host credentials and files reachable from containers, virtual machines, and shared folders
- Data retained in snapshots, workspace logs, and unused environments

## 16.9 Social engineering, compromise, and security awareness

- Social engineering aimed at developers: phishing, impersonation of colleagues or services, malicious repositories, coding tests, and pull requests
- Verifying unexpected requests for credentials, code execution, or access through a separate trusted channel
- Indicators of a compromised workstation, credential, repository, or developer account
- First responses to suspected compromise: stopping the suspicious activity, preserving information, revoking exposed credentials and sessions, and reporting through the organization's incident process
- Sources of security information for languages, frameworks, dependencies, and tools: security advisories, vendor bulletins, organizational guidance, and OWASP resources
