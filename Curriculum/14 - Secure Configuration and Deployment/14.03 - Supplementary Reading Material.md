# Supplementary reading – Secure Configuration and Deployment

This chapter covers configuring applications and their environments securely and protecting the process that deploys them.

## Secure configuration principles

### Misconfiguration

An application's security depends on its code and on the settings of everything around it.
These include the web server, application framework, database, container, hosting platform, and deployment pipeline.
A security misconfiguration is a setting that weakens security, such as an enabled debug mode, a default password, or a publicly readable storage bucket.
Misconfiguration can expose an application whose code contains no vulnerabilities.
The [OWASP Top 10:2025 A02 – Security Misconfiguration](https://owasp.org/Top10/2025/A02_2025-Security_Misconfiguration/) describes common examples.

### Secure defaults and hardening

A secure default is a setting that is safe without further action.
Many products ship with defaults chosen for ease of setup instead, such as sample applications, default administrator accounts, or features enabled for demonstration.
Change default credentials before deployment, and remove sample content and unused accounts.

Hardening means reducing a component's exposure by disabling or removing what the application does not need.
Examples include unused services, modules, accounts, and HTTP methods such as `TRACE`.
Each removed feature is one less place for a vulnerability or a configuration mistake.

The attack surface is the set of points where an attacker can interact with a system.
Reducing it applies to the application's own features, to its servers, and to the platform that hosts it.

### Consistent and reviewable configuration

Configuration that is changed by hand on each server is hard to review and easy to get wrong.
Define configuration in files under version control, such as server configuration, container definitions, and infrastructure as code.
Infrastructure as code describes servers, networks, and cloud resources in files that tools use to create them.
Changes can then be reviewed and tested like code, and every environment can be built the same way.

Configuration drift occurs when a running system no longer matches its defined configuration, for example after an emergency manual change.
Drift hides settings from review and can undo hardening.
Record emergency changes and bring them back into the defined configuration.

## Web and application server configuration

### Serving only what is intended

A web server should serve only the application's public files.
Point it at a dedicated public directory rather than at the project root.
When the whole project is served, files such as these may become downloadable:

- Source control metadata, such as the `.git` directory, which can contain the full source code and history
- Environment files, such as `.env`, which often contain secrets
- Configuration files, backups, and editor temporary files
- Build scripts, dependency manifests, and internal documentation

Configure the server to deny requests for hidden files and for file types the application does not serve.
Disable directory listings, which show every file in a directory when no index page exists, unless a listing is intended.

### Upload directories and file permissions

Directories that store uploaded or generated files must not allow those files to run as code.
If an attacker can upload a script and the server executes it, the attacker can run commands on the server.
Module 12 covers file upload handling.

File permissions should separate application code from runtime data.
The application usually needs to read its code but not change it.
Grant write access only to the specific directories that need it, such as a cache or upload directory.
If an attacker gains control of the application, read-only code limits their ability to install persistent changes.

### Administrative interfaces and information

Administrative consoles, monitoring endpoints, health dashboards, and internal API documentation help operators but also help attackers.
Restrict them to authorized users, and where possible to internal networks.
Do not leave them reachable on the public internet with default or no authentication.

Servers and frameworks often announce their name and version in response headers, default pages, and error pages.
This information helps attackers find known vulnerabilities.
Remove or reduce it where the platform allows, and keep components updated, because hiding a version does not fix it.

## Preparing a release for production

### Debug features and test content

Development settings favor convenience and detail.
Production settings must favor safety.

Before release, check that:

- Debug modes, development servers, and interactive debugging tools are disabled
- Diagnostic and profiling endpoints are removed or restricted
- Test accounts, test-only routes, sample data, and seeded credentials are absent
- Feature flags for unfinished or internal features are off in production

Some framework debug tools let a user run code on the server from the browser.
Leaving one enabled in production can give an attacker full control of the application.
Module 6 covers the difference between development and production error output.

### What the deployed artifact contains

The deployed artifact should contain only what the application needs to run.
Development dependencies, build tools, compilers, and test frameworks add code that can contain vulnerabilities.
Most package managers can install production dependencies only.

A multi-stage build separates building from running.
The first stage has the tools to compile and package the application.
The final stage copies only the result into a minimal runtime image.

Review the contents of web-facing directories for files that do not belong there:

- Source maps, which map minified client code back to its original source, including comments
- Backup copies such as `config.php.bak` or `index.old`
- Archives, database exports, and log files
- Documentation that describes internal systems

Source maps for public client code are sometimes published intentionally.
Decide this explicitly, and check that they contain no secrets, internal comments, or server code.

## Configuration and secrets in deployment

### Separating configuration from code

Configuration that differs between environments, such as database addresses, feature settings, and credentials, should not be compiled into the application.
Keep it separate so that the same tested build can be deployed to test and production with different settings.
Each environment needs its own credentials.
A test system should not be able to reach production data with production credentials.

### Providing secrets at runtime

Deployed applications need secrets such as database passwords and API keys.
Store them in a secret store, such as a cloud secret manager or a dedicated secrets management service, or in the hosting platform's protected settings.
The application or the platform retrieves them at startup or when needed.

Many platforms can give an application a managed identity, an identity issued and rotated by the platform.
The application uses it to obtain short-lived credentials for other services, so no long-lived password needs to be stored.

Secrets can leak through deployment materials:

- Container images, where a secret copied into a layer stays readable even if a later layer deletes it
- Deployment files and infrastructure as code committed to version control
- Environment variables printed by diagnostic pages, crash reports, or logs
- Error output that includes connection strings

Grant each application access only to the secrets it needs.
Rotate secrets on a schedule and revoke them immediately after suspected exposure.
Module 16 covers handling secrets on developer workstations, and the [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) covers secret stores in depth.

## Runtime identities and environment hardening

### Least-privilege identities

Run each application or service under its own dedicated identity without administrator rights.
If an attacker compromises the application, they gain only that identity's permissions.

Sharing one identity across several services means that compromising one service gives access to the resources of all of them.
Separate identities also make logs show which component performed an action.

Limit each identity's permissions to what the component needs:

- File system access to its own code and data directories
- Database permissions for the tables and operations it uses, rather than database administrator rights
- Network access to the services it calls
- Cloud permissions for specific resources rather than whole accounts

### Containers and services

Containers are often run with more privilege than they need.
Basic container hardening includes:

- Running as a non-root user inside the container
- Using minimal base images that contain only required packages
- Mounting the container's file system as read-only, with explicit writable locations
- Dropping Linux capabilities the application does not need
- Setting memory and CPU limits so one container cannot exhaust the host

The [OWASP Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) describes these controls.

Applications that run directly on a server can use similar protections from the operating system's service manager.
For example, systemd can run a service as a dedicated user, make most of the file system read-only to it, and limit its resources.

### Network exposure

Expose only the ports and services that clients need.
Databases, caches, and internal services should not be reachable from the internet.
Restricting outbound connections to the services the application calls also limits what an attacker can reach after a compromise, including through server-side request forgery.

## Security headers and browser policies

### Setting headers consistently

HTTP response headers tell browsers how to treat a response.
Security headers are usually set in the web server, a reverse proxy, or framework middleware so that every response receives them.
Check that error pages, redirects, and static files receive the same headers as application pages.

Common security headers include:

- `X-Content-Type-Options: nosniff`, which stops browsers from guessing a different content type than the one declared, for example treating an uploaded text file as a script
- `Referrer-Policy`, which limits how much of the current URL the browser sends to other sites in the `Referer` header
- `Cache-Control: no-store` on responses with sensitive data, which prevents browsers and shared caches from storing them

The [OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html) lists recommended values.

HTTP Strict Transport Security (HSTS) is also delivered as a header.
[Module 9](../09%20-%20Secure%20Communications/) covers how it works.

### Content Security Policy

Content Security Policy (CSP) tells the browser which sources a page may load scripts, styles, images, and other resources from.
A strict policy limits the damage of cross-site scripting.
[Module 4](../04%20-%20Input%20Validation%20and%20Output%20Encoding/) covers CSP as a defense in depth against cross-site scripting, after output encoding.

Deploying a CSP on an existing application can break legitimate features.
A report-only mode sends the policy with `Content-Security-Policy-Report-Only`, so the browser reports violations without blocking them.
Review the reports, adjust the policy, and then enforce it.
Keep reporting enabled after enforcement to detect new violations.

The `frame-ancestors` directive controls which sites may embed the page in a frame.
Clickjacking tricks a user into clicking on a hidden, framed page, for example to approve an action.
Setting `frame-ancestors 'none'` or `'self'` prevents this for pages that should not be framed.
The older `X-Frame-Options` header provides similar protection in browsers that do not support `frame-ancestors`.

### Cross-Origin Resource Sharing

The same-origin policy stops scripts on one site from reading responses from another site.
An origin is the combination of scheme, host, and port, such as `https://shop.example`.
Cross-Origin Resource Sharing (CORS) lets a server tell the browser that specific other origins may read its responses.
CORS relaxes a protection, so its configuration needs care.

Unsafe CORS configurations include:

- Copying the request's `Origin` header into `Access-Control-Allow-Origin` without checking it against an allowlist
- Trusting the `null` origin, which sandboxed pages and local files can send
- Loose matching, such as accepting any origin that ends with `example.com`, which also matches `attacker-example.com`

These mistakes are most serious when the response also includes `Access-Control-Allow-Credentials: true`.
Then any site the user visits can read data from the application using the user's session.
Browsers refuse the wildcard origin `*` together with credentials, which is why misconfigured servers often reflect the request's origin instead.

CORS only controls which origins can read responses in a browser.
It does not stop requests from being sent, and it does not apply to clients other than browsers.
The server must still authenticate and authorize every request, and state-changing requests still need protection against cross-site request forgery.

## Managed platforms and cloud services

### Shared responsibility

On a managed platform, the provider and the customer share security responsibilities.
In platform-as-a-service and serverless hosting, the provider usually maintains the servers and operating system.
The customer remains responsible for the application, its data, its identities, and the platform settings it chooses.
Read the provider's documentation to learn where the boundary lies for each service.

### Settings the application team controls

Typical platform settings include:

- Enforcing HTTPS and setting the minimum TLS version
- Restricting network access, for example allowing only a front-end gateway to reach the application
- Enabling the platform's authentication options where used
- Disabling remote debugging, remote shell access, and file transfer endpoints that the team does not use
- Using managed identities and the platform's secret references instead of stored credentials

Cloud storage, databases, and message queues used by the application have their own access settings.
A storage bucket configured for public access can expose every file in it.
Grant access to specific identities instead, and generate time-limited links for files that must be shared.

### Separating environments

Platforms often provide staging slots, preview deployments, or branch environments.
These can be reachable from the internet and may run untested code.
Protect them with authentication, keep production data and credentials out of them, and remove them when no longer needed.
Check that swapping a staging slot into production does not carry staging settings with it.

## Deployment pipelines and releases

### Pipeline and deployment identities

A deployment pipeline needs permission to change production, which makes it a valuable target.
Give each pipeline only the permissions its deployment requires.
A pipeline that deploys one application should not be able to change unrelated systems.

Many platforms support federated credentials for pipelines.
The pipeline proves its identity to the cloud provider with a short-lived token, often using OpenID Connect (OIDC), and receives temporary credentials.
This avoids storing long-lived deployment keys in the pipeline's settings.

Pipeline secrets must not be available to untrusted code.
Builds of pull requests from outside contributors should run without access to deployment credentials.
Configure the pipeline to mask secrets in logs, and avoid commands that print the environment.
[Module 10](../10%20-%20Software%20Supply%20Chain%20Security/) covers build isolation and artifact integrity.

### Controlling what reaches production

Protect the branches that deploy to production.
Require reviews before changes are merged, prevent direct pushes, and restrict who can approve production deployments.
Many platforms let teams define protected environments that require approval before a deployment job runs.

Commit signing attaches a cryptographic signature to each commit.
It shows which key signed the commit, which helps detect commits that impersonate another author.
It does not show that the change is safe, and a stolen signing key produces valid signatures.

Third-party pipeline components, such as reusable actions or plugins, run with the pipeline's permissions.
Pin them to a specific verified version, such as a full commit hash, rather than a tag that can be moved to different code.

Deploy only artifacts that passed the required checks, and verify them before deployment as described in Module 10.
Keep the previous release available so the team can roll back quickly if a deployment fails or causes harm.

## Verifying configuration

Automated checks find many configuration mistakes before they reach production.
Scanners can check infrastructure as code, container images, and server configuration against known insecure settings.
Run them in the pipeline and review their findings like other test results.

After deployment, test the running application from outside:

- Request `/.git/`, `/.env`, backup files, and other sensitive paths and check that they are not served
- Check that directory listings are disabled
- Trigger an error and check that no debug output appears
- Check that security headers are present on application pages, error pages, and static files
- Send requests with an untrusted `Origin` header and check that CORS does not allow it

Monitor production configuration for drift, and review configuration changes in the same way as code changes.
The [OWASP Web Security Testing Guide: Configuration and Deployment Management Testing](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/02-Configuration_and_Deployment_Management_Testing/README) describes how testers check these settings.

## Reviewing a first production deployment

Consider a fictional team preparing to deploy a customer portal to a managed hosting platform for the first time.
The application is packaged as a container image and deployed by a pipeline.
Before the release, the team runs its pre-production checks against the staging environment.

The external checks find that `/.git/config` is downloadable.
The container image copies the entire project directory into the web root.
The team changes the image build to a multi-stage build that copies only the compiled application and its public assets into a minimal runtime image.
The image now also runs as a non-root user.

The debug toolbar appears on error pages in staging.
The framework enables debug mode unless an environment variable disables it, and the variable is missing in staging.
The team changes the configuration so that debug mode is off unless explicitly enabled, which makes a missing setting fail safely.

An image scan reports a database password in an image layer.
The password was copied in an early build step and deleted later, but it remains in the layer.
The team rotates the password, removes it from the build, and configures the application to use the platform's managed identity to obtain database access at runtime.

A CORS test shows that the API reflects any `Origin` header and allows credentials.
Any website could read a signed-in customer's data.
The team replaces the reflection with an allowlist containing only the portal's own origin.

Finally, the pipeline deploys with a long-lived administrator key stored in its settings.
The team switches to federated short-lived credentials scoped to the portal's resources and requires approval before production deployments.

The team adds each of these checks to the pipeline so they run on every future release.
