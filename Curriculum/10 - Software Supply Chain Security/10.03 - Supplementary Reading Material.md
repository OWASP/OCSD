# Supplementary reading – Software Supply Chain Security

This chapter covers selecting, verifying, and maintaining software components.

## Software supply chain risks

A software supply chain includes the code, components, tools, and services involved in producing and delivering software.
A web application may depend on a server framework, client-side libraries, container images, build plugins, and package registries.
Internally developed and proprietary components also belong to this supply chain.

A direct dependency is a component the application explicitly requires.
A transitive dependency is introduced through another component.
For example, a document-generation library may depend on an image-processing library.
The application's security can depend on both.

Build plugins can read source code or access credentials available to the build process.
Libraries in the deployed application can access its data and resources.
A component used only during building can therefore affect the security of the released software.

A vulnerable component contains a weakness that could be exploited.
Malicious code is deliberately written or modified to perform unauthorized actions.
A component may contain both vulnerabilities and malicious code.

An artifact is an output that can be stored or distributed, such as a package or container image.

Common ways untrusted code enters a supply chain include:

- Typosquatting, using a package name that resembles the intended package
- Dependency confusion, resolving an internal package name from an unintended external source
- Maintainer compromise, using stolen access to publish changes under an established project identity
- Artifact tampering, replacing or modifying a package, image, or other release output
- Build compromise, changing how reviewed source code becomes the software delivered to users

A compromised release can affect every application that uses it.
The [OWASP Software Supply Chain Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Software_Supply_Chain_Security_Cheat_Sheet.html) covers threats across these stages.

## Selecting third-party components

Adding a component creates ongoing work: reviewing its behavior, monitoring vulnerability reports, testing updates, and replacing it when support ends.
Start by identifying the required functionality and checking whether an existing dependency or platform feature already provides it.
For security-sensitive functions, established libraries and framework features can reduce mistakes in custom code.

A component review considers:

- Purpose, whether the component fits the application's intended use
- Identity, whether the package and repository belong to the expected project or supplier
- Maintenance, whether the chosen version has support and a path to security updates
- Security response, how maintainers receive vulnerability reports and address problems
- Behavior, including required permissions, network access, and installation scripts
- Dependencies, including the extra components introduced by the selected version
- Licensing, including the terms that apply to the intended use and distribution

Download counts and release frequency are unreliable measures of security.
A mature library may need few releases.
Published reports and fixes show how maintainers respond to vulnerabilities.
A project with no published vulnerabilities may have received little security review.

Review the package identity and source even when the name looks familiar.
Changes in ownership, publishing infrastructure, or requested permissions deserve investigation.
Review components more closely when they can access sensitive data or critical systems.

### Licensing considerations

Open-source licenses permit commercial use and can impose obligations on users and distributors.
Typical obligations include preserving copyright notices or making covered source code available under specified conditions.

Common distinctions include:

- Permissive licenses, which generally allow broad reuse while retaining requirements such as preserving notices
- Copyleft licenses, which require covered code to remain under specified terms when relevant conditions are met
- Source-available software, whose source can be read but whose license may restrict uses permitted by open-source licenses

The actual obligations depend on the license terms and how the software is used, modified, or distributed.
Some licenses also include conditions related to providing access over a network.
Follow the organization's review process and consult the responsible specialist when obligations or compatibility are unclear.
Record the license for the version being adopted and check for changes during updates.

## Managing dependencies

Package managers use configured registries and resolution rules to find packages and select versions.
An approved registry may be a public project registry or an organization-managed repository.

Configure internal package names or namespaces to resolve from their intended source.
Unexpected fallback to a public registry can introduce the wrong package.
Review changes to registry configuration alongside dependency changes.

Version constraints specify which versions a package manager may select.
A lockfile records resolved versions and, depending on the ecosystem, sources and integrity information.
Use the package manager's supported method to record and review the selected versions.
Pinning fixes a dependency to a specific version.
Monitor that version for vulnerabilities and review updates before changing it.

A lockfile can also preserve a package obtained from the wrong source.
Check the registry settings, package identity, and selected versions together.
Checksums can detect changed downloads without controlling which versions are selected.

A dependency cooldown delays adoption of a package version for a set period after publication.
This gives maintainers and researchers time to detect and report problems.
Older versions can still contain vulnerable or malicious code.
An urgent security fix may justify a documented exception to the waiting period.

Dependency updates can change transitive packages, installation scripts, permissions, and licenses.
Review those changes with release notes and relevant source changes before accepting the update.
Installation scripts and build plugins may run as soon as a package is installed or built.
Their access to files, networks, and credentials should be limited to what the task requires.

Container base images and remotely loaded client-side scripts also require maintenance.
Review and test their updates alongside application packages.

Remove unused dependencies and their unneeded transitive components.
For unsupported components, plan replacement or another maintained source of fixes.
Record temporary exceptions with an owner and a review date.

## Component inventories and vulnerability analysis

A software bill of materials (SBOM) records the components identified in a software product or release.
It helps locate applications that contain a component and releases that need attention.

Useful inventory information includes:

- Component name, version, and package identifier
- Supplier or source information
- Relationships between direct and transitive components
- License information
- The application release or artifact the inventory describes
- The inventory's creation time and scope

A manifest, lockfile, and SBOM serve different purposes:

- Package manifests declare dependencies and version constraints for a project.
- Lockfiles record the versions selected by a package manager.
- SBOMs list the components identified in a product or release.

Inventory coverage depends on the inputs and tools used to produce it.
Reading an application manifest can miss bundled libraries, container packages, or files added during building.
Check whether the inventory represents the delivered artifact and record known gaps.
Assess the security of the listed components separately.

CycloneDX and SPDX are standards for exchanging component information.
The [OWASP CycloneDX project](https://owasp.org/www-project-cyclonedx/) provides documentation and tools for creating and reading SBOMs.
Generate an inventory for each release and retain it with the corresponding artifact information.

### Software composition analysis

Software composition analysis (SCA) identifies dependencies and compares component information with vulnerability data.
Some tools also report license or maintenance concerns.
[OWASP Dependency-Check](https://owasp.org/www-project-dependency-check/) is an example of a tool that reports known vulnerabilities in dependencies.
[OWASP Dependency-Track](https://owasp.org/www-project-dependency-track/) consumes SBOMs to monitor component risk across application releases.

A security advisory describes a vulnerability and the software it affects.
Check each finding against the package, version, and advisory.
An incorrect package match can produce a false positive: a reported issue that does not affect that component.
A missed dependency or an incomplete advisory database can produce a false negative: an issue that exists but is not reported.
Check that the tool's vulnerability data is current.

Continue monitoring after release because new vulnerabilities can be disclosed in unchanged code.
Retained inventories help locate affected releases, including older versions still in service.

## Source, build, and artifact integrity

Protect source code and build settings from unauthorized changes.
Verify that released artifacts come from the expected source and build process.

### Source and build changes

Dependency declarations, lockfiles, and build configuration affect the contents of a release.
Keep them under version control and require review before they enter the release process.
Restrict who can change release settings or publish artifacts.

Continuous integration and continuous delivery (CI/CD) systems may build code from untrusted contributors.
Keep those builds isolated from release credentials and publishing permissions.
Fresh, isolated build environments reduce the risk that leftover files or processes affect later builds.
The [OWASP CI/CD Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/CI_CD_Security_Cheat_Sheet.html) provides further guidance on these controls.

### Hashes, signatures, and provenance

A cryptographic hash function calculates a value from a file's contents.
This value is a cryptographic checksum, also called a digest.
Compare the downloaded file's checksum with the one published by a trusted source.
If the checksums differ, the file's contents differ too.
An attacker who can replace both the file and the published checksum can make them match.

A container image tag can refer to different content over time.
Selecting an image by digest identifies specific content.
Review and update that selection when a new image is needed, including for security fixes.

A digital signature connects signed content to a signing key.
Verify the signature and check that its signer is trusted to publish the artifact.

Provenance records information about an artifact's origin and production.
For a build artifact, this can include the source revision, build process, inputs, and producing system.
Check that the provenance is authentic and refers to the correct artifact.
Compare the recorded source and build process with those expected for the release.

A trusted maintainer can publish vulnerable code, and a compromised build system can produce a harmful artifact with a valid signature.
Include source review, dependency checks, and tests in the release process.

Apply the required checks before installing a package, deploying an image, or accepting an update.
Reject and investigate artifacts that fail those checks.
Changing the expected checksum or disabling verification to make a build pass bypasses these checks.

### Third-party web resources

A third-party script loaded into a web page normally runs with access to that page's data and behavior.
Changes to the hosted script can therefore affect users without a new application deployment.

Subresource Integrity (SRI) lets the browser check a script or stylesheet against a checksum specified by the application.
The browser rejects content that does not match.
The application must obtain and protect the expected checksum.
Cross-origin resources require appropriate Cross-Origin Resource Sharing (CORS) headers from their host.

SRI checks the resource to which its integrity metadata applies.
Additional scripts loaded by that resource need their own protections.
Review changes to the resource before updating the expected checksum.
The [OWASP Third Party JavaScript Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Javascript_Management_Cheat_Sheet.html) discusses these risks and controls.

## Dependency assessment and response

Review how a component's known vulnerabilities, code, and configuration affect the application.

### Source review and testing

Static application security testing (SAST) analyzes code for weaknesses without running the application.
SCA checks dependencies against known vulnerability information.

SAST can scan available dependency source code when the tool supports it.
Its findings depend on the languages, rules, and code paths the analysis covers.
Check that the scanned source matches the dependency version used by the application.

SAST can miss weaknesses or malicious behavior.
Review its findings for false positives.

Review changed permissions, network access, installation scripts, and calls to the component.
Unit and integration tests check whether the update preserves expected behavior.
Security regression tests check that existing protections still work.
For example, an invoice-generation library may create temporary files containing customer data.
A regression test checks that an update preserves file permissions that prevent other local users from reading this data.

Package and artifact checks also need tests:

- The approved component resolves from its configured source
- An internal package is never fetched from an unintended public source, including when the internal registry is unavailable
- An artifact that matches the expected checksum and passes any required signature checks is accepted
- Changed content or an unexpected signer is rejected before the artifact is used

### Responding to a vulnerable component

An advisory may identify affected versions, conditions for exploitation, and a fixed version.
Prioritize fixes by the affected component's use, exposure, potential impact, and evidence of exploitation.
Severity scores are one input to that decision.

Check whether the affected component is present in the deployed artifact or used during building.
Determine whether the relevant feature and configuration are in use, including indirect calls through other libraries.
Tools may miss some execution paths, so finding no calls to vulnerable code does not rule out its use.
Record why a fix is deferred and what remains uncertain.

Possible responses include:

- Updating to a maintained version that addresses the issue
- Removing an unused component or affected feature
- Replacing the component when a suitable fix is unavailable
- Applying a temporary mitigation with an owner and a review date
- Asking the responsible decision-maker to accept the remaining risk

Test the selected change and verify its effect in the resulting artifact.
For an update or removal, check all included copies of the affected component.
Update the release inventory and document any remaining mitigations or accepted risks.
The [OWASP Vulnerable Dependency Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Vulnerable_Dependency_Management_Cheat_Sheet.html) discusses responses when immediate updates are difficult.

### Responding to suspected malicious code

Investigate what a suspected malicious component may already have accessed or changed.
Stop further use and distribution of the suspect component and notify the responsible security and release teams.
Preserve relevant artifacts, logs, and release records for their investigation.

The response may include isolating affected build environments, revoking exposed credentials, and rebuilding from trusted inputs.
Investigate earlier releases for data access and credential theft, even after replacing the component.
The response team determines which systems are affected and how to recover.

## Reviewing a dependency update

Consider a fictional invoice application that uses a library to generate documents.
Customers can upload a logo to include on their invoices.
A proposed library update introduces a transitive image-processing component.
SCA reports an advisory for the selected version of that component.
The advisory describes a flaw that can interrupt document generation when the component processes a malformed image.

The developer confirms the package identity and affected version against the advisory.
The release notes identify a later document-library version that selects a fixed image-processing component.
The developer proposes that version and reviews its dependency changes, source, installation behavior, and licenses.

The team reviews registry settings, package sources, and resolved versions before installing the update.
Both components must come from the approved registry.
Downloaded artifacts must match recorded, trusted checksums.
A test confirms that mismatched artifacts are rejected before installation.

Integration tests confirm that invoices with supported logo images render correctly.
Security regression tests check that malformed images are rejected while other invoice requests continue to succeed.

Before release, the team checks the components against the advisory to confirm that the fixed version is included and the affected version is absent.
The SBOM identifies the new release and lists both the direct library and the transitive image-processing component.

If unexpected network access or a verification failure suggests compromise, the team investigates before continuing the update.
It also checks whether the suspect component ran during earlier builds or entered previous releases.
Record the selected versions, completed checks, and test results with the release.
