# Module 6 – Error Handling

This outline defines the error handling knowledge assessed in Module 6.

## 6.1 Errors and their security impact

- Errors, exceptions, and unexpected conditions such as missing data, invalid input, unavailable dependencies, and exhausted resources
- Security effects of poor error handling: information disclosure, bypassed security checks, inconsistent application state, and reduced availability
- Why failure paths need the same security review and testing as successful paths

## 6.2 Information disclosure through errors

- Internal details that error responses can reveal: stack traces, source file paths, framework and component versions, database errors and queries, internal hostnames, and configuration values
- How disclosed details help attackers plan further attacks
- Generic user-facing messages and a reference identifier that links the response to internal diagnostic information
- Error messages that help users correct their input without revealing internal details
- Observable differences between error responses, including messages, status codes, response times, and redirects
- How such differences reveal whether accounts, records, or resources exist
- Consistent responses for cases that must not be distinguishable, such as failed sign-in for unknown and known accounts

## 6.3 Failing securely

- Fail-secure and fail-open behavior and their consequences
- Denying access when an authentication or authorization check cannot be completed
- Secure outcomes when a security-relevant dependency, such as an authorization service or certificate check, is unavailable or returns an error
- Default values, initial states, and fallback logic that grant access after an error
- Rolling back or compensating partially completed operations so that security-relevant state remains consistent
- Releasing locks, connections, files, and other resources on failure paths
- Errors that consume excessive resources and affect availability

## 6.4 Exception handling practices

- Handling specific exception types rather than catching all errors in one place
- Handling an error at the layer that has enough context to decide on a safe response
- Risks of empty or swallowing exception handlers that hide failures
- Unhandled exceptions and the framework's default behavior when they occur
- Wrapping exceptions to keep the original cause for internal diagnosis without exposing it to users
- Translating internal errors at trust boundaries, such as between an application and its clients or between services

## 6.5 Centralized error handling and error responses

- Global exception handlers and middleware that produce consistent error responses
- Custom error pages that replace framework and server default pages
- Consistent error formats for APIs, such as Problem Details for HTTP APIs
- HTTP status codes that indicate the error category without revealing internal details
- Error responses for every response path, including asynchronous processing and errors raised before application code runs

## 6.6 Error modes and configuration

- Differences between development and production error settings
- Risks of debug modes, verbose error output, and diagnostic endpoints in production
- Secure defaults that disable detailed error output unless explicitly enabled for development
- Environment-based configuration and checks that detect detailed error output in production

## 6.7 Error diagnosis and testing

- Error information to record internally: time, request or correlation identifier, error type, affected operation, and relevant context
- The boundary with Module 7, which covers which data must not be logged and how log data is protected
- Test cases that trigger errors and check user-facing responses for internal details
- Tests that check security checks deny access when they fail
- Tests that compare responses for cases that must not be distinguishable
- Checks that production configuration does not expose detailed errors
