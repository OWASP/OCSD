# Module 10 – Software Supply Chain Security

This outline defines the software supply chain knowledge assessed in Module 10.

## 10.1 Software supply chain risks

- Parts of a software supply chain: source code, repositories, dependencies, build tools, and distribution services
- Risks in internally developed, open-source, and proprietary components
- Direct and transitive dependencies used during development, builds, and runtime
- The difference between vulnerable components and deliberately malicious code
- How typosquatting, dependency confusion, maintainer compromise, and release tampering introduce untrusted code
- Effects of compromised components on application data, build credentials, and downstream users

## 10.2 Selecting third-party components

- Whether existing libraries or platform features meet a need before adding a component
- Maintenance, support, vulnerability reporting, and past responses to security issues
- Checks of the package's identity, source repository, supplier, and release process
- Intended use, required permissions, installation behavior, and transitive dependencies
- Why popularity, frequent releases, and no reported vulnerabilities do not guarantee security
- Identifying licenses and obligations for using, modifying, and distributing software
- Permissive and copyleft licenses, source availability, and the need to check license terms
- When licensing or security questions need organizational approval or specialist review

## 10.3 Managing dependencies

- Approved registries and settings that map package names or namespaces to their sources
- How version constraints and lockfiles determine installed versions, and how integrity metadata detects changed downloads
- Review of direct and transitive dependencies before adding or updating a package
- Version pinning and the need to monitor and update pinned versions
- Dependency cooldowns, their limitations, and exceptions for urgent security fixes
- When installation scripts and build plugins run and what they can access
- Removal of unused components and replacement of unsupported dependencies
- Review of updates to container base images and dependencies outside the package manifest

## 10.4 Component inventories and vulnerability analysis

- The purpose of a software bill of materials (SBOM) for a product or release
- Inventory contents: component identities, versions, relationships, licenses, and the associated artifact
- Coverage of direct, transitive, bundled, and container components, including gaps in generated inventories
- CycloneDX and SPDX standards for exchanging component information
- Differences between a package manifest, a lockfile, and an SBOM
- How software composition analysis (SCA) identifies dependencies and matches them to known vulnerabilities
- Incorrect matches, missing components, and incomplete advisory data in SCA results
- Retaining release inventories to check for newly reported vulnerabilities after deployment

## 10.5 Source, build, and artifact integrity

- Review and access controls for source code, dependency declarations, and build configuration
- Keeping builds that run untrusted code isolated from release credentials and publishing permissions
- What hashes and digital signatures verify about an artifact
- Why expected checksums and signer identities must come from trusted sources
- Provenance records linking an artifact to its source and build process
- Limits of signatures and provenance when the source or build process is compromised
- Verification of third-party packages, container images, and updates before installation or deployment
- Subresource Integrity (SRI) checks for web resources and the need to protect their expected checksums
- Rejection and investigation of artifacts that fail verification

## 10.6 Dependency assessment and response

- Static application security testing (SAST) of available dependency source code and how it differs from SCA
- Manual review of findings, code changes, and security-sensitive behavior
- False positives, false negatives, and gaps in automated analysis
- Vulnerability priority based on the affected version, application use, exposure, impact, and available fixes
- Responses to dependency risks: updates, removal, replacement, temporary mitigation, and documented risk acceptance
- Containment and reporting of suspected malicious code or a compromised release process
- Functional, integration, and security regression tests for dependency changes
- Positive and negative tests for package resolution and artifact verification
- Checks that the release and its inventory reflect the chosen fix
