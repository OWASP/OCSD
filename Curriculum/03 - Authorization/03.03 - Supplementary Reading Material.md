# Supplementary reading – Authorization

This chapter explains how web application developers define, enforce, and test authorization.

## Authorization decisions

Authentication establishes the identity associated with a request.
Authorization determines whether the request may perform an action on a resource.
A valid login does not grant access to every feature or record in an application.
Public resources may allow access without an authenticated identity.

An authorization decision uses several kinds of information:

- Subject, the user or service requesting access
- Action, the operation being requested, such as read, update, approve, or delete
- Resource, the record, file, function, or other protected object
- Policy, the rules that determine which requests are permitted
- Context, relevant information such as ownership, tenant, resource state, or time

Consider a customer who requests an invoice.
Authentication tells the application which customer made the request.
Authorization checks whether that customer may read that specific invoice.
The decision may depend on ownership, membership of the invoice's organization, or a support permission.

Access control protects confidentiality, integrity, and availability:

- An unauthorized read can disclose information.
- An unauthorized update can corrupt data.
- An unauthorized delete or administrative action can make a service unavailable.

## Defining an access policy

Authorization requirements should identify the subject, action, resource, and conditions for access.
An authorization matrix provides a compact representation of those rules.

| Subject | Resource and action | Decision |
| --- | --- | --- |
| Anonymous visitor | Read the public product catalog | Permit |
| Customer | Read an invoice owned by that customer | Permit |
| Customer | Read another customer's invoice | Deny |
| Support agent | Read a customer invoice with the support permission | Permit |
| Customer | Refund an invoice | Deny |

The matrix becomes a shared input for implementation, code review, and testing.
It should cover protected functions and data across all application interfaces.
A web application may expose the same operation through a user interface, an API, and a background process.
Each access path must enforce the applicable policy.

Several principles guide the policy:

- Least privilege, each subject receives only the permissions required for its work
- Deny by default, a request is denied unless a rule grants access
- Complete mediation, every protected operation receives an authorization decision
- Separation of duties, incompatible parts of a sensitive operation require different permissions or actors

Permissions should describe allowed actions in terms meaningful to the application.
Examples include `invoice:read`, `invoice:refund`, and `user:change-role`.
Application code can ask for a permission while the policy determines which roles, attributes, or relationships provide it.
This separation makes authorization rules easier to change and review.

## Access-control models

Access-control models provide different ways to express a policy:

- Access control list, permissions are recorded for subjects or groups on a resource
- Role-based access control, permissions are assigned to roles and roles are assigned to users
- Attribute-based access control, rules evaluate attributes of the subject, resource, action, and environment
- Relationship-based access control, rules evaluate relationships such as owner, member, parent, or delegate

Role-based access control works well when stable job functions determine access.
For example, an accounting role may include permission to issue refunds.
Role checks become difficult to maintain when application code contains many hard-coded role names.
Checking the required permission allows the policy to evolve without changing every protected function.

Attribute-based access control supports rules that depend on several facts.
A document may be available to an employee in the same organization while the document remains in a reviewable state.
The employee's organization is a subject attribute, and the document state is a resource attribute.

Relationship-based access control expresses rules based on how a subject relates to a resource.
An owner may edit a document, a project member may read it, and a delegated reviewer may approve it.
These relationships are common in collaborative and multi-tenant web applications.

Applications often combine models.
A support agent may need a role-based permission and a relationship with the customer's organization.
The selected rules should remain understandable, testable, and consistent with least privilege.

## Enforcing authorization

Authorization must be enforced where the requester cannot bypass or modify the decision.
For a web application, this is usually trusted server-side application code or another trusted service layer.

Hiding a control in the user interface improves usability by avoiding unavailable actions.
The server provides security by rejecting requests that lack the required permission.
A caller can construct requests without using the application's user interface.

Every protected operation needs a check for the current subject, action, and resource.
Checks should cover every endpoint and HTTP method that reaches the operation.
They also apply to static files, exports, background jobs, and calls between services when those paths can reach protected resources.

Client input remains untrusted until the application validates it.
The application derives the subject and tenant context from verified authentication and authorization data.
It treats request parameters that claim a role, permission, ownership relationship, or tenant as untrusted.
It then validates that context against the requested resource.

Reusable authorization mechanisms reduce gaps between features and code paths.
Middleware can enforce broad requirements, such as restricting an administrative endpoint.
Business or data-access code may still need rules based on a particular record, field, tenant, or workflow state.

Framework annotations and middleware can provide reliable enforcement when configured correctly.
Developers verify their defaults, coverage, and failure behavior.
A missing annotation, an alternate route, or an unmatched rule must not grant access.

## Function-, object-, and property-level authorization

Authorization checks apply at several levels:

- Function-level authorization, whether the subject may perform an operation such as refunding an invoice or changing a user's role
- Object-level authorization, whether the subject may access a specific invoice, document, account, or file
- Property-level authorization, whether the subject may read or change a specific field of an object

Function-level failures often produce vertical privilege escalation.
A regular user reaches an administrative endpoint or calls a privileged HTTP method directly.

Object-level failures often produce horizontal privilege escalation.
A user changes an invoice identifier and receives another customer's invoice.
This failure is commonly called an insecure direct object reference or broken object-level authorization.

The format of an identifier does not establish permission.
Random identifiers and universally unique identifiers can make resources harder to guess.
The application still checks authorization whenever a resource is requested.

Property-level rules apply to both input and output.
A customer may update a shipping address while the account status and credit limit remain protected.
An application that binds every submitted field to an internal object may allow unauthorized changes through mass assignment.
A response can also disclose protected fields when serialization returns more data than the caller may read.

Tenant membership is part of the authorization context in a multi-tenant application.
Queries, cache keys, file paths, and other resource lookups need the trusted tenant context.
A resource identifier supplied by the client must not move an operation into another tenant.

## Testing authorization

Authorization tests begin with the policy or authorization matrix.
Each permitted rule needs a positive test.
Each access boundary needs a negative test.

Useful test identities include:

- An unauthenticated user
- A user with the expected permission
- A user without that permission
- Two users with the same role who own different resources
- Users from different tenants
- A user whose privileges were reduced or removed

Tests should call protected operations directly.
They cover relevant HTTP methods, alternate endpoints, object identifiers, and resource states.
Property-level tests verify both submitted fields and returned fields.

A horizontal authorization test creates a resource as one user and requests it as another user with similar privileges.
A vertical authorization test calls a privileged function as a lower-privileged user.
A tenant-isolation test requests data from one tenant while using the identity of another tenant.

Unit tests can evaluate policy decisions for many combinations of inputs.
Integration tests verify that endpoints and data-access paths invoke those decisions correctly.
Authorization tests belong in the regression suite because new features and routes can introduce missing checks.
The test matrix changes when the access policy changes.

## Turning an access policy into implementation and tests

Consider an endpoint that returns an invoice identified in the request URL.
The access policy permits a customer to read an invoice that belongs to that customer.
It also permits a support agent to read invoices for an assigned tenant when the agent has the `invoice:read` permission.
All other requests are denied.

These policy rules produce specific requirements:

- Derive the subject identity and tenant context from verified authentication data.
- Permit a customer only when the invoice belongs to that customer.
- Permit a support agent only when the agent has the required permission and is assigned to the invoice's tenant.
- Deny the request when no rule grants access.

The endpoint loads the invoice within the trusted tenant context.
It asks the authorization mechanism whether the current subject may perform `invoice:read` on that invoice.
The endpoint returns the invoice only after a permit decision.

The requirements produce positive and negative tests:

- The customer who owns the invoice can read it.
- Another customer with the same role cannot read it.
- A support agent with the required permission can read an invoice in an assigned tenant.
- A support agent without the permission cannot read the invoice.
- A support agent assigned to another tenant cannot read the invoice.
- Calling the endpoint directly produces the same decisions as using the user interface.

The team can trace each test to an access-policy rule and its enforcement point.
When the policy changes, the implementation and its tests change with it.
